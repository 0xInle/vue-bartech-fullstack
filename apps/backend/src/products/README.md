# API продукции

`ProductsController` обслуживает пользовательскую работу с активной продукцией и архивом.
`InternalServiceProductsController` открывает только чтение, поиск, создание и редактирование продукции
в рамках подтверждённой `ServiceSession`; архив, экспорт и управление организацией здесь недоступны.

`ProductContextAccess` проверяет клиентские полномочия через `OrganizationsService`, а для внутреннего
контекста повторно проверяет активную auth-сессию, grant, `service_access`, компанию и заведение через
`SupportAccessService`. Внутренние мутации сохраняют null в пользовательских полях автора и атомарно
записывают `AuditEvent` и `InternalAuditEvent` с внутренним актором и ID сессии.

`InternalCatalogController` — отдельный backoffice API для очереди неоднозначных локальных ингредиентов.
Он требует внутреннюю сессию и разрешение `global_catalog`, не открывает `ServiceSession` и возвращает
только поля ингредиента и сведения о совпадении. Решения выполняются сервисом `catalog-review` в
`@bartech/backend-products`; при связывании или создании он заменяет ссылки состава только в исходном
заведении, пишет tenant- и внутренний аудит и удаляет локальную карточку атомарно. Маршрут не
предоставляет просмотр компании, заведения и рецептур.

Тот же контроллер предоставляет `/internal/catalog/manage/*` для активных глобальных карточек,
алиасов и слияния. Все операции повторно проверяют глобальную область и статус карточки в
`catalog-management`. Слияние блокирует две строки карточек, сравнивает `updatedAt`, проверяет
конфликты до записи и одной транзакцией обновляет все ссылки `ProductComponent` с глобальной областью,
переносит атрибуты и алиасы, удаляет дубликат и пишет события в оба журнала аудита.

`/internal/catalog/manage/categories` предоставляет управление общим деревом категорий под тем же
разрешением. `catalog-categories` сериализует изменения дерева транзакционной блокировкой, запрещает
нарушать глубину и системные ограничения `other`, а каждое изменение вместе с аудитом сохраняет
атомарно. При редактировании существующей глобальной или локальной карточки неактивную категорию
можно оставить без изменения; назначить её заново нельзя.

Предметные правила описаны в `PRODUCT_MODEL.md`, `ROLES_AND_PERMISSIONS.md` и `DATA_MODEL.md`.
