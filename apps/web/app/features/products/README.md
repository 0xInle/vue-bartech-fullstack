# Выбор продукции

Feature `products` содержит клиентский поиск и минимальный элемент выбора ингредиента для форм,
которые будут реализованы на следующем продуктовом этапе. Здесь нет страницы или отдельной
навигации.

`useWorkspaceProductSearch` обслуживает пользовательский поиск с Главной и из оболочки. Для
обычных ролей он вызывает поиск выбранного заведения; шеф-бармен может явно включить поиск по
компании. Отмена запросов и ключ TanStack Query учитывают компанию, заведение, роль, область,
строку и выбранный тип. `WorkspaceProductSearch` показывает состояния поиска, а
`ProductSearchResultDrawer` загружает read-only карточку результата другого заведения, не меняя
маршрут рабочего пространства. Результаты ингредиентов остаются неинтерактивными. Результаты
показываются в PrimeVue `DataTable` малого размера с одиночным выбором и ограничением первыми 20
строками. Для ингредиентов в колонке категории отображается имя товарной категории, для остальных
типов — тип продукта; фильтры и пагинация не показываются.

Для рабочего поиска используются отдельный `/products/workspace-search` в контексте заведения и
страничный `/products/search` в контексте компании. Обычный `/products/search?scope=COMPONENT`
сохраняет прежний ответ в виде массива для выбора ингредиентов и заготовок в формах.
Страница поиска проверяет объектный контракт пагинированных маршрутов до показа результата; ответ
неподдерживаемой формы переводит запрос в состояние ошибки, а не в пустую выдачу.

Серверный company-scope поиск и получение карточки доступны только после повторной проверки
членства шеф-бармена и компании/заведения по базе. Пользовательский поиск отделён от
`useProductSearch`, который продолжает обслуживать подбор компонентов техкарт.

## Части

- `composables/useProductSearch.ts` выполняет запрос через сгенерированный API-клиент, передаёт
  сигнал отмены и держит результат в TanStack Query с ключом, включающим компанию и заведение.
- `components/IngredientSelector.vue` связывает поле PrimeVue AutoComplete с поиском и возвращает
  выбранную типизированную карточку через `v-model`.

Поиск вызывается после двух символов; задержка ввода задаётся компонентом. Backend повторно проверяет
доступ и возвращает только глобальные ингредиенты и локальные продукты текущего заведения.
Обновление контракта выполняется через `pnpm api:generate`; generated-код нельзя править вручную.
Operation-функции и модели доступны через публичный barrel `@bartech/api-client`. Файл
`packages/api-client/src/index.ts` не генерируется Orval и связывает сгенерированные operations и
модели, поэтому публичные типы остаются доступны после повторной генерации. `types.ts` выводит из
operation-ответов общие для компонентов поиска типы без дублирования DTO.
В нём также нормализуется `venueId` результата поиска: в текущем OpenAPI-контракте nullable-поле
описывается слишком широко, а интерфейс работает только со строковым идентификатором или `null`.
