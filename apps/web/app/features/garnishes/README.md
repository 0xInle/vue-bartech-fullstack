# Гарниры

Модуль `garnishes` реализует список активных гарниров текущего заведения, технологическую
карту по прямому адресу, создание и редактирование в Drawer. Входные страницы Nuxt импортируют только экраны
модуля: запросы, состояние и обработка формы находятся внутри `features/garnishes`.

## Границы компонентов

- `GarnishListScreen.vue` показывает список с поиском по названию, состояния загрузки, ошибки
  и пустого результата; управляет открытием Drawer и переходом на созданную карточку.
- `GarnishCardScreen.vue` показывает состав, технологию, необязательные выход и комментарий,
  а для `manage_products` открывает форму редактирования.
  Заготовка в составе является ссылкой на собственную карточку, без раскрытия рецептуры деревом.
  Недоступные карточки показывают одно сообщение без различения причины отказа.
- `GarnishFormDrawer.vue` обслуживает режимы `create` и `edit`, предзаполняя форму карточкой
  и упорядоченными строками состава с ID единиц. Координирует VeeValidate/Zod-валидацию
  и сохранение. Общая ошибка
  находится сверху, полевые ошибки — возле контролов; ответ API не закрывает форму и не
  сбрасывает ввод. Закрытие изменённой формы требует подтверждения. На телефоне Drawer занимает
  всю ширину экрана. Во время сохранения закрытие заблокировано.
- `GarnishComponentRows.vue` управляет строками состава и переиспользует публичные
  `IngredientSelector` и `LocalIngredientCreateForm` из `features/products`. Созданный ингредиент
  назначается исходной строке по её стабильному ключу; фокус возвращается к пустому количеству,
  иначе — к единице. Вложенная форма ингредиента не находится внутри формы гарнира.
- `useGarnishes.ts` владеет запросами, URL-состоянием и памятью прокрутки. Параметр
  `{ list: false }` в карточке и Drawer отключает дополнительный запрос списка и синхронизацию
  его URL-состояния.

## Маршруты и состояние

- Список: `/app/companies/:companyId/venues/:venueId/garnishes`.
- Карточка: `/app/companies/:companyId/venues/:venueId/garnishes/:garnishId`.

У создания нет отдельного URL: форма открывается только в Drawer справа. Поиск хранится в
`query`; фильтров и сортировки в списке нет, записи всегда идут по названию. Устаревший параметр
`sort` удаляется при открытии списка. Ссылка на карточку переносит поисковый запрос, ссылка
«Гарниры» возвращает его обратно.
Прокрутка хранится в `sessionStorage` под ключом `garnish-list-scroll:<companyId>:<venueId>` и
восстанавливается однократно после успешного запроса и отрисовки списка (`nextTick`).

Ключ списка: `garnish-list`, компания, заведение и поисковый запрос. API получает только запрос;
backend использует сортировку по названию по умолчанию. Ключ карточки:
`garnish-card`, компания, заведение, ID гарнира. Справочники используют общий ключ
`product-references`, компанию и заведение. После создания инвалидируются только список
текущего заведения и карточка нового гарнира. После редактирования инвалидируются список и
карточка изменённого гарнира. PATCH возвращает структурированный конфликт со списком и отпечатком,
если гарнир используется активными коктейлями. После подтверждения сервер повторно вычисляет
зависимости под блокировкой заведения, атомарно сохраняет карточку с составом и записывает
`product.updated`. Неизменённая форма не меняет `updatedAt`. Выбор гарниров для коктейля
обновляется собственным запросом существующего модуля коктейлей, без дополнительной связки экранов.

## Доступ и допустимый состав

Навигация видна при `view_products`; создание и редактирование — только при `manage_products`. Backend остаётся
единственным источником прав, состояния и области данных. Состав выбирается через существующий
поиск `COMPONENT`: глобальные и локальные ингредиенты, а также заготовки текущего заведения.
Гарниры и коктейли в составе запрещены сервером. Создание и все проверки записи остаются
в `ProductsService.createGarnish`; обновление выполняет отдельный `GarnishUpdateService`, а
backend-модуль чтения отвечает только за чтение.

Нет категории, отдельной страницы создания или редактирования, архива, удаления, истории, выгрузки,
автоматического вычисления выхода или создания заготовки/гарнира из строки состава.

Frontend использует сгенерированные API-методы и `requestApi`; запись повторяет общий cookie/CSRF
паттерн. Типы извлекаются из публичных сгенерированных псевдонимов операций (`MutationBody`,
ответов `Response200`/`Response201`): они ссылаются на DTO контракта, но не требуют ручного
добавления экспорта моделей в сгенерированный клиент. API-клиент обновляется только штатной
`pnpm api:generate`; сгенерированные файлы вручную
не редактируются. Фактически выполненные проверки и ограничения указаны в плане
`docs/plans/2026-10-14-stage-7-garnishes-first-slice.md`.
