# План разработки MVP BarTech

> **Для агентов-исполнителей:** перед реализацией отдельного этапа обязательно создать и согласовать его детальный план с помощью `superpowers:writing-plans`. Для выполнения утверждённого плана использовать `superpowers:subagent-driven-development` или `superpowers:executing-plans` только после выбора пользователя. Пункты этого документа используют флажки `- [ ]` для отслеживания общего прогресса.

**Цель:** последовательно построить и подготовить к пилотному использованию MVP BarTech, сохранив утверждённые продуктовые правила и возможность расширять систему без переделки её ядра.

**Архитектура:** pnpm-monorepo с Nuxt 4 PWA и модульным монолитом NestJS. PostgreSQL является источником бизнес-данных, Redis и BullMQ выполняют фоновые задачи, файлы хранятся в S3-совместимом хранилище. Разработка идёт вертикальными срезами: каждый этап объединяет данные, backend, API и необходимый интерфейс.

**Технологии:** Nuxt 4, Vue 3, PrimeVue 4, Tailwind CSS, TanStack Query, VeeValidate, Zod, NestJS 11, Express, PostgreSQL, Prisma, Redis, BullMQ, OpenAPI, Orval, Pino, Docker, GitHub Actions.

**Спецификации:** `ARCHITECTURE.md`, `MVP_SCOPE.md`, `DATA_MODEL.md`, `UI_AND_NAVIGATION.md`, `REGISTRATION_FLOW.md`, `AUTHENTICATION_FLOW.md`, `ROLES_AND_PERMISSIONS.md`, `PRODUCT_MODEL.md`, `COMPANY_AND_VENUE_LIFECYCLE.md`.

## Глобальные ограничения

- Документация и пользовательские сообщения пишутся на русском языке; код и машинные идентификаторы — на английском.
- Используются только актуальные стабильные версии по официальной документации на момент начала реализации.
- Supabase не используется и не добавляется в проект.
- Backend является единственным доверенным источником прав, состояний и бизнес-правил.
- Данные компаний и заведений не смешиваются ни в запросах, ни в кеше frontend.
- Микросервисы, GraphQL, Kubernetes, RLS, realtime и offline-first не входят в MVP.
- Тестовые библиотеки и тестовые файлы не добавляются без отдельного согласования пользователя.
- Unit, integration и e2e-тесты не запускаются без прямой команды пользователя.
- `lint`, `typecheck`, `format` и `build` не считаются тестами и используются для статической проверки реализации.
- Тесты после реализации MVP добавляются точечно, прежде всего для ролей, разрешений, передачи управления и tenant-изоляции.
- Существующий прототип не определяет архитектуру новой системы и удаляется по мере создания нового monorepo.
- Любое новое бизнес-правило сначала согласовывается и фиксируется в правильном документе, а не появляется только в коде.
- Перед реализацией этапа исполнитель читает все указанные для него источники, а не только этот план.

## Основные риски для ревью

1. **Чужая компания или заведение в идентификаторе запроса.** Backend должен вернуть отказ и не раскрыть существование объекта; отдельные проверки после MVP закрепят tenant-изоляцию.
2. **Одновременное изменение ролей или уход управляющих.** Каждое действие повторно проверяет актуальный состав и не оставляет действующее заведение без допустимого управления.
3. **Сбой Redis или почтового провайдера после записи в PostgreSQL.** Критичное фоновое действие не теряется благодаря Transactional Outbox и идемпотентному worker.
4. **Повторное или конфликтующее принятие приглашения.** Только один допустимый процесс завершается, постоянные данные не создаются частично.
5. **Архивирование, восстановление или сопоставление связанного продукта.** Ссылки на компоненты остаются целостными, а пользователь получает явный выбор для конфликтов.

Эти риски проверяются при ревью каждого затронутого этапа. Автоматические проверки для них проектируются только после MVP и отдельного согласования.

## Как пользоваться планом

Этот документ является главным маршрутом, а не покомандной инструкцией на весь проект. Для каждого этапа действует один процесс:

1. Выбрать только следующий незавершённый этап, зависимости которого уже выполнены.
2. Прочитать перечисленные источники и текущее состояние кода.
3. Выписать вопросы, на которые документация не отвечает.
4. Задать пользователю по одному значимому вопросу с рекомендуемым вариантом.
5. При необходимости создать короткую спецификацию в `docs/specs/` и добавить её в `DOCUMENTATION_MAP.md`.
6. Создать детальный план этапа в `docs/plans/` с точными файлами, интерфейсами и статическими проверками.
7. Получить подтверждение пользователя и выбранный способ исполнения.
8. Реализовать только утверждённый объём.
9. Выполнить разрешённые `lint`, `typecheck` и `build` для затронутых workspace.
10. Провести отдельное ревью кода без самовольного запуска тестов.
11. Обновить статус этапа и техническую документацию, если реализация уточнила архитектурный контракт.

Если этап обнаруживает необходимость изменить глобальную архитектуру, его реализация останавливается до обновления `ARCHITECTURE.md`. Если обнаружено новое продуктовое правило, сначала обновляется соответствующий предметный документ.

## Документы этапов

```text
docs/
├── specs/                       # короткие спецификации модулей при наличии пробелов
└── plans/                       # детальные исполнимые планы отдельных этапов
```

Не требуется создавать спецификацию ради формальности. Если существующая документация однозначно определяет модуль, создаётся только его детальный план реализации.

## Этап 0. Рабочий процесс разработки

**Результат:** агенты и человек используют одинаковые правила, документацию и точки контроля до начала продуктового кода.

**Источники:** `DOCUMENTATION_MAP.md`, `ARCHITECTURE.md`, глобальные и проектные инструкции Codex.

### Работы

- [ ] Создать проектного агента-программиста с обязательным чтением актуальной документации и официальных источников установленных версий.
- [ ] Создать агента-ревьюера архитектуры и кода, который не редактирует реализацию без отдельной команды.
- [ ] Создать агента-тестировщика, но запретить его автоматический вызов до прямой команды пользователя.
- [ ] Оставить документационного аналитика отдельной ролью, вызываемой только явно.
- [ ] Зафиксировать в проектных инструкциях запрет самовольного создания и запуска тестов.
- [ ] Описать короткий цикл «спецификация → план → реализация → статическая проверка → ревью».
- [ ] Убедиться, что команды агентов универсальны и не содержат захардкоженных имён отдельных документов.

### Критерии завершения

- Все инструкции агентов написаны на русском языке.
- Обязанности программиста, ревьюера, тестировщика и аналитика не пересекаются.
- Ни один агент не вызывается автоматически вопреки пользовательскому правилу.
- Пользователь понимает, как вручную вызвать каждую роль из интерфейса.

## Этап 1. Технический фундамент monorepo

**Результат:** чистый monorepo запускает пустые Nuxt и NestJS приложения, подключается к инфраструктуре и генерирует типизированный API-клиент.

**Источники:** `ARCHITECTURE.md` — репозиторий, frontend, backend, API, данные, наблюдаемость, развёртывание и качество кода.

### Планируемая структура

```text
pnpm-workspace.yaml
package.json
apps/web/
apps/backend/
packages/database/
packages/api-client/
packages/backend-*/
tooling/
infrastructure/
```

### Работы

- [ ] Удалить старые `frontend/` и `backend/` после отдельной проверки, что в них не осталось нужных данных или пользовательских изменений.
- [ ] Создать корневой `pnpm-workspace.yaml` и единые команды workspace.
- [ ] Создать `apps/web` на Nuxt 4 без Pinia и Supabase.
- [ ] Создать `apps/backend` на NestJS 11 со стандартным Express adapter.
- [ ] Настроить строгий TypeScript, общий ESLint flat config, Prettier и EditorConfig.
- [ ] Создать базовые Nuxt-макеты и место для локальных Layers без реализации продуктовых экранов.
- [ ] Создать Prisma multi-file schema и контролируемую конфигурацию миграций.
- [ ] Подключить Pino, `requestId`, глобальный формат Problem Details и `/health/live`, `/health/ready`.
- [ ] Подключить OpenAPI и Orval на одном минимальном служебном endpoint.
- [ ] Подготовить локальные Docker-сервисы PostgreSQL, Redis, MinIO и Mailpit; ClamAV можно подключить на этапе поддержки.
- [ ] Создать безопасную проверку переменных окружения без хранения секретов в Git.
- [ ] Создать начальный GitHub Actions pipeline для `lint`, `typecheck`, Prisma, Orval и `build` без тестов.

### Статическая проверка

- `pnpm lint` завершается без ошибок.
- `pnpm typecheck` завершается без ошибок.
- `pnpm build` собирает `web`, `backend` и worker entrypoint.
- Повторная генерация Orval не создаёт незакоммиченных изменений.
- Prisma schema проходит проверку, а миграции создаются только из `packages/database`.

### Критерии завершения

- Старый прототип не участвует в сборке.
- Nuxt и NestJS запускаются как независимые процессы из одного workspace.
- Frontend получает типизированный ответ служебного endpoint через сгенерированный клиент.
- Инфраструктурные зависимости заменяемы через конфигурацию.

## Этап 2. Идентификация и первая компания

**Результат:** новый пользователь проходит согласованный путь с лендинга, создаёт аккаунт, компанию и первое заведение и становится бар-менеджером; существующий пользователь может тем же публичным путём создать ещё одну независимую компанию без второго аккаунта.

**Источники:** `AUTHENTICATION_FLOW.md`, `REGISTRATION_FLOW.md`, `COMPANY_AND_VENUE_LIFECYCLE.md`, `DATA_MODEL.md`, соответствующие разделы `MVP_SCOPE.md` и `UI_AND_NAVIGATION.md`.

### Область этапа

- `User`, `UserProfile`, `RegistrationAttempt`, `Session`, подтверждение email и восстановление пароля;
- минимальные `Company`, `Venue`, членство и роль первого бар-менеджера;
- единая атомарная регистрация без постоянных черновиков;
- создание новой компании и первого заведения существующим авторизованным пользователем с сохранением прежних мест работы;
- вход, выход, смена пароля и управление сессиями;
- состояния активного, служебно заблокированного и ожидающего удаления аккаунта;
- техническая основа запуска, семидневного ожидания, отмены и окончательного удаления аккаунта по правилам документации;
- публичные экраны лендинга, регистрации и авторизации;
- серверная cookie-сессия, CSRF и ограничения попыток входа;
- обязательные письма через Outbox, BullMQ и `EmailService`.

### Обязательные границы

- Аккаунт, компания и заведение не создаются частично.
- Первый пользователь не выбирает произвольную должность и становится бар-менеджером первого заведения.
- Незавершённый путь можно начать заново по правилам документации.
- Создание дополнительной компании начинается с лендинга, а не из рабочего пространства действующего заведения.
- На этом этапе полный цикл удаления доступен для аккаунта без действующих рабочих членств. Интеграция с выходом, передачей полномочий и удалением сотрудника завершается на этапе 4.
- Пять неудачных попыток входа ограничивают новые попытки на 15 минут и предлагают восстановление пароля.
- Сессии действуют 30 дней с последней активности и не более 90 дней.

### Критерии завершения

- Успешный путь заканчивается рабочей сессией и доступом к созданному заведению.
- Ошибка на любом шаге не оставляет частично созданную компанию или членство.
- Один аккаунт может независимо работать в нескольких компаниях и создать новую компанию без потери существующих ролей.
- Ожидание удаления ограничивает рабочий доступ, допускает согласованную отмену и после истечения срока приводит к обезличиванию или удалению данных согласно `AUTHENTICATION_FLOW.md`; сценарий с действующими рабочими членствами пока явно недоступен.
- Email и фоновые задачи не блокируют HTTP-ответ дольше необходимого.
- Пользовательские ошибки соответствуют `AUTHENTICATION_FLOW.md` и не раскрывают наличие чужого аккаунта.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 3. Рабочее пространство и полномочия

**Результат:** авторизованный пользователь попадает в правильный контекст компании и заведения, а backend централизованно рассчитывает его реальные разрешения.

**Источники:** `ROLES_AND_PERMISSIONS.md`, `DATA_MODEL.md`, `UI_AND_NAVIGATION.md`, `ARCHITECTURE.md`.

### Область этапа

- CRM-layout на компьютере и мобильная навигация;
- контекст `/app/companies/{companyId}/venues/{venueId}`;
- переключение доступных компаний и заведений;
- `PermissionService`, типизированный каталог разрешений, Guard и предметные проверки;
- локальные роли, роль шеф-бармена, делегированные права и временная ответственность;
- единый экран отсутствующего или недоступного материала;
- профиль с компаниями, заведениями, должностями и сессиями.

### Обязательные границы

- Frontend скрывает недоступные действия, но не принимает решение о доступе.
- Каждый защищённый repository-запрос содержит нужную область компании или заведения.
- Шеф-бармен не получает локальную роль в той же компании.
- Одна локальная роль пользователя действует только внутри конкретного заведения.
- Отозванное разрешение прекращает действие без устаревшего серверного кеша.

### Критерии завершения

- Подмена `companyId` или `venueId` не открывает чужие данные.
- Интерфейс всегда показывает текущий рабочий контекст.
- Один и тот же пользователь может безопасно переключаться между независимыми компаниями.
- Матрица разрешений реализована централизованно, а не повторяется в контроллерах.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 4. Команда, приглашения и расширение компании

**Результат:** уполномоченные сотрудники управляют командой, приглашают сотрудников и бар-менеджеров новых заведений и выполняют плановую передачу управления.

**Источники:** `REGISTRATION_FLOW.md`, `ROLES_AND_PERMISSIONS.md`, `COMPANY_AND_VENUE_LIFECYCLE.md`, `DATA_MODEL.md`, `UI_AND_NAVIGATION.md`.

### Рекомендуемое разбиение детальных планов

1. Приглашение в существующее заведение.
2. Приглашение шеф-бармена в компанию.
3. Приглашение бар-менеджера с созданием нового заведения.
4. Изменение ролей и делегированных прав.
5. Удаление, самостоятельный выход и непрерывность управления.
6. Создание дополнительного заведения существующим управляющим.
7. Состояния компаний и заведений, их настройки и закрытие.

### Область жизненного цикла

- состояния компании и заведения, допустимые переходы и серверные проверки;
- настройка компании и заведений в пределах полномочий пользователя;
- закрытие заведения без пользовательского архива закрытых заведений;
- пустая компания с шеф-барменом и создание в ней нового заведения;
- автоматическое удаление компании без заведений и пользователей по правилам MVP;
- запуск закрытия компании шеф-барменом, 168 часов на отмену и окончательное удаление данных компании;
- отмена закрытия компании и режим только для чтения на время ожидания;
- закрытие связанных приглашений и прекращение членств в соответствии с предметными документами.
- завершение общего сценария удаления аккаунта с проверкой всех его компаний, заведений и обязанностей;

### Обязательные границы

- Одно приглашение относится к одной почте, цели и роли.
- Приглашение действует 24 часа до начала принятия; начатая сессия действует по правилам документации.
- Постоянные данные появляются только после полного успешного завершения.
- Конфликтующие приглашения и роли повторно проверяются в транзакции.
- Действующее заведение не остаётся без локальной команды или допустимого управления.
- Закрытие заведения и компании является отдельным осознанным действием; обычного безвозвратного удаления заведения из рабочего интерфейса нет.
- Перед закрытием пользователь получает возможность выгрузить данные после появления выгрузки на этапе 8; до этого закрытие не считается полностью готовым пользовательским сценарием.
- Поддержка не выбирает управляющего по своему усмотрению.
- Все изменения ролей и управления создают записи аудита; пользовательский экран истории появляется на этапе 8.

### Критерии завершения

- Все три типа приглашений приводят ровно к согласованному членству.
- Повторная обработка ссылки не создаёт второе членство.
- Бар-менеджер и шеф-бармен видят только допустимые им команды.
- Плановый уход управляющего либо безопасно передаёт полномочия, либо блокируется понятной причиной.
- Закрытая сущность сразу перестаёт быть рабочим контекстом, а завершение ожидания закрытия компании нельзя обойти устаревшей сессией или фоновой задачей.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 5. Продуктовое ядро и каталоги

**Результат:** база и backend представляют единый составной продукт, глобальные ингредиенты, локальные ингредиенты и зависимости без дублирования моделей.

**Источники:** `PRODUCT_MODEL.md`, `DATA_MODEL.md`, `MVP_SCOPE.md`, `ARCHITECTURE.md`.

### Область этапа

- глобальный каталог готовых ингредиентов;
- временные локальные ингредиенты конкретного заведения;
- единая модель `Product` и `ProductComponent` для коктейлей, заготовок и гарниров;
- единицы измерения и утверждённые справочники;
- правила допустимых вложений и защита от циклов;
- уникальность активных названий внутри типа и заведения;
- обязательные и необязательные поля, включая фактический выход;
- начальный контролируемый способ наполнения глобального каталога владельцем продукта.

### Обязательные границы

- Глобальный ингредиент не копируется в каждое заведение.
- Локальный ингредиент невидим другим заведениям.
- Заготовка может включать другую заготовку без автоматического расчёта её выхода.
- Гарнир не включает другой гарнир.
- Состав не допускает прямой или косвенный цикл.
- Тип продукта не меняется после создания без отдельного согласованного сценария.

### Критерии завершения

- Все виды продукции используют одну согласованную модель состава.
- Ограничения целостности защищены базой и предметным кодом.
- Продуктовые repository-операции всегда ограничены текущим заведением или глобальным каталогом.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 6. Поиск и сопоставление ингредиентов

**Результат:** пользователь быстро находит продукцию и ингредиенты, а локальные ингредиенты безопасно обрабатываются для расширения глобального каталога.

**Источники:** разделы поиска и глобального каталога в `PRODUCT_MODEL.md`, `MVP_SCOPE.md`, `UI_AND_NAVIGATION.md` и `ARCHITECTURE.md`.

### Область этапа

- PostgreSQL Full Text Search, `pg_trgm` и необходимые GIN-индексы;
- нормализация регистра, пробелов, `е/ё`, алиасов и транслитерации;
- ранжирование точного, префиксного, алиасного и нечёткого совпадения;
- глобальный поиск и поиск внутри выбора компонента;
- кандидаты на сопоставление локального ингредиента с глобальным;
- автоматическое применение только надёжного совпадения;
- очередь неоднозначных кандидатов для backoffice;
- атомарное переназначение ссылок после подтверждения совпадения.

### Критерии завершения

- Поиск всегда учитывает область доступа до формирования результата.
- Типичный запрос укладывается в целевые 200–300 мс в подготовленном наборе данных.
- Опечатка или известный алиас не требуют точного совпадения строки.
- Неоднозначный кандидат не изменяет продукцию автоматически.
- Сопоставление не создаёт копию глобального ингредиента в заведении.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 7. Коктейли, заготовки и гарниры

**Результат:** сотрудники просматривают технологические карты, а пользователи с разрешением создают и редактируют продукцию через адаптивный интерфейс.

**Источники:** `PRODUCT_MODEL.md`, `UI_AND_NAVIGATION.md`, `ROLES_AND_PERMISSIONS.md`, `MVP_SCOPE.md`.

### Nuxt Layers

- `layers/cocktails`;
- `layers/preparations`;
- `layers/garnishes`;
- общая основа `shared/product-core` для строк состава и выбора компонентов.

### Область этапа

- списки и карточки продукции;
- отдельная страница технологической карты;
- создание и редактирование без черновиков;
- динамический состав на VeeValidate и Zod;
- создание локального ингредиента из выбора компонента;
- технология приготовления, комментарий и необязательный фактический выход;
- предупреждение о зависимых активных продуктах перед изменением общей заготовки или гарнира;
- правило «последнее успешно сохранённое изменение становится актуальным»;
- адаптивность для CRM на компьютере и мобильного PWA.

### Критерии завершения

- Бармен может быстро найти и прочитать техкарту без лишних управляющих элементов.
- Пользователь с разрешением может полностью создать каждый из трёх видов продукции.
- Недопустимая зависимость или неверная единица блокируется с понятной ошибкой.
- Компоненты одного слоя не импортируют внутренние файлы другого слоя.
- Версии содержимого и изображения в MVP не создаются.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 8. Архив, аудит и выгрузки

**Результат:** продукцию можно безопасно архивировать и восстанавливать, значимые действия видны в журнале, а данные заведения можно выгрузить.

**Источники:** `PRODUCT_MODEL.md`, `MVP_SCOPE.md`, `DATA_MODEL.md`, `UI_AND_NAVIGATION.md`, `COMPANY_AND_VENUE_LIFECYCLE.md`.

### Область этапа

- единый архив продукции;
- проверка активных зависимостей перед архивированием;
- восстановление с каскадным предупреждением, заменой или восстановлением зависимостей;
- окончательное удаление продукции по правилам MVP;
- `AuditEvent` и пользовательский экран истории;
- PDF отдельной техкарты;
- структурированная выгрузка выбранных или всех техкарт;
- BullMQ-задача, S3-файл и краткоживущая ссылка на скачивание;
- предложение выгрузки перед закрытием заведения или компании;
- включение выгрузки в уже подготовленные на этапе 4 сценарии закрытия; только после этого закрытие считается готовым для пилота.

### Обязательные границы

- Архивная запись не выбирается для новой активной техкарты.
- Восстановление не изменяет другие архивные карточки без явного выбора.
- Журнал показывает действие, но не хранит старое содержимое карточки.
- Закрытые заведения не появляются в пользовательском архиве MVP.
- Выгрузка не заменяет системную резервную копию.

### Критерии завершения

- Ни одна операция архива не оставляет недействительную активную ссылку.
- Повтор фоновой задачи не создаёт несколько одинаковых файлов.
- Пользователь скачивает только файл компании или заведения, к которому сохраняет доступ.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 9. Поддержка и backoffice BarTech

**Результат:** пользователь создаёт обращение и осознанно выдаёт временный доступ, а внутренний сотрудник работает только в разрешённой области.

**Источники:** разделы поддержки в `MVP_SCOPE.md`, `DATA_MODEL.md`, `UI_AND_NAVIGATION.md`, `ARCHITECTURE.md`.

### Область этапа

- обращения со статусами «Новое», «В работе» и «Закрыто»;
- допустимый технический контекст без содержимого техкарт;
- загрузка вложения в карантин S3;
- проверка типа, размера и содержимого через ClamAV worker;
- отдельный `InternalUser`, внутренний вход и обязательная MFA;
- `SupportAccessGrant` на семь дней и `ServiceSession`;
- служебная работа с продукцией без клиентской роли и impersonation;
- backoffice обработки глобального каталога и локальных кандидатов;
- немедленное прекращение доступа при отзыве или истечении срока;
- отдельный аудит служебных действий.

### Критерии завершения

- Обращение без действующего разрешения не открывает данные компании.
- InternalUser не может использовать клиентское приглашение или роль.
- Вредоносный или непроверенный файл недоступен для скачивания.
- Служебная сессия не позволяет управлять командой, ролями, компанией и безопасностью.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 10. PWA, SEO, аналитика и эксплуатация

**Результат:** приложение устанавливается, публичная часть индексируется, эксплуатационные сбои обнаруживаются, а владелец продукта видит минимальные метрики использования.

**Источники:** `MVP_SCOPE.md`, `UI_AND_NAVIGATION.md`, эксплуатационные разделы `ARCHITECTURE.md`.

### Область этапа

- PWA manifest, иконки, установка и плашка доступного обновления;
- кеш только оболочки и статических ресурсов;
- постоянное состояние отсутствия сети и блокировка изменений;
- SSR или prerender лендинга, метаданные, sitemap, robots и базовая Schema.org-разметка;
- русскоязычная семантика лендинга без обещания гарантированного первого места Google;
- `ProductAnalytics` с закрытым перечнем событий без персональных данных и содержимого техкарт;
- минимальный внутренний экран продуктовых показателей;
- централизованные ошибки, Pino, корреляционные идентификаторы и health-checks;
- контроль BullMQ, резервных копий и критических зависимостей;
- безопасные HTTP-заголовки, CSP, CSRF, rate limiting и проверка production-зависимостей.

### Критерии завершения

- Приложение устанавливается в поддерживаемых браузерах и корректно сообщает об отсутствии сети.
- Лендинг доступен поисковым роботам и содержит валидные метаданные.
- Аналитика не собирает запрещённые значения.
- Пользователь получает `requestId` при общей технической ошибке.
- Система различает живой процесс и готовность принимать трафик.
- Затронутые workspace проходят `lint`, `typecheck` и `build`.

## Этап 11. Приёмка и пилот MVP

**Результат:** production-развёртывание готово к бесплатному тестированию на реальных знакомых заведениях.

**Источники:** раздел «Условия приёмки MVP» в `MVP_SCOPE.md`, весь набор утверждённых документов.

### Область этапа

- production Docker-образы `web`, `backend` и `worker`;
- российская инфраструктура для данных, аналитики, файлов и резервных копий;
- reverse proxy на одном origin;
- GitHub Actions с автоматической тестовой средой и ручным production-релизом;
- применение миграций отдельным контролируемым шагом;
- ежедневные зашифрованные резервные копии с ориентировочным хранением 30 дней;
- фактическая проверка восстановления;
- ручное наполнение стартового глобального каталога владельцем продукта;
- проверка ключевых пользовательских путей только после прямой команды пользователя;
- исправление блокирующих дефектов перед приглашением пилотных пользователей;
- сбор обратной связи без оплаты и подписки.

### Критерии завершения

- Выполнены условия приёмки из `MVP_SCOPE.md`.
- Владелец продукта подтвердил готовность стартового глобального каталога.
- Production-релиз требует ручного подтверждения и имеет понятный откат приложения.
- Резервная копия не только создаётся, но и проверена восстановлением.
- Пилотные пользователи могут пройти регистрацию, работать с продукцией и командой и обратиться за помощью.
- Нереализованные функции удалены из интерфейса и репозитория, а не оставлены неработающими заготовками.

## Этап 12. Точечные тесты после MVP

**Результат:** после стабилизации функциональности наиболее рискованные правила защищены небольшим набором автоматических проверок.

Этот этап начинается только после отдельного решения пользователя. До него не устанавливаются тестовые библиотеки и не создаётся тестовая инфраструктура.

### Приоритет 1 — backend-правила

- [ ] tenant-изоляция компаний и заведений;
- [ ] матрица ролей и итоговых разрешений;
- [ ] делегирование и отзыв разрешений;
- [ ] передача временной ответственности;
- [ ] удаление и самостоятельный выход управляющих;
- [ ] конфликтующие приглашения и повторное завершение;
- [ ] транзакционная целостность создания компании и заведения;
- [ ] циклы и допустимые зависимости продукции;
- [ ] архивирование и восстановление зависимостей.

### Приоритет 2 — несколько e2e-сценариев

- [ ] создание первой компании;
- [ ] приглашение сотрудника;
- [ ] создание и поиск техкарты;
- [ ] архивирование и восстановление;
- [ ] выдача и отзыв служебного доступа.

Frontend unit-тесты добавляются только для сложной самостоятельной логики, которую дешевле проверять изолированно. Простое отображение компонентов не тестируется ради процента покрытия.

## Критерий изменения порядка

Этап можно перенести раньше только тогда, когда он не зависит от незавершённой модели данных, разрешений или API. Визуальный экран без устойчивого backend-контракта не считается основанием нарушить порядок.

Если пилот требует раннего показа интерфейса, допускается отдельный выбрасываемый прототип. Его код не переносится в production без обычного этапа спецификации, плана и ревью.
