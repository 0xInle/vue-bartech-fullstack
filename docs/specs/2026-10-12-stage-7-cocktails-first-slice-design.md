# Спецификация первого среза этапа 7: коктейли

## Цель

Дать барной команде первый законченный сценарий работы с технологическими картами: найти коктейль текущего заведения, открыть его карточку и создать новый коктейль из доступных компонентов. Срез должен быть полезен сам по себе и использовать поиск ингредиентов, реализованный на этапе 6.

## Источники требований

- `DOCUMENTATION_MAP.md` — иерархия документации;
- `MVP_SCOPE.md` — основной путь MVP и границы продукции;
- `PRODUCT_MODEL.md` — состав, допустимые связи и создание временного локального ингредиента;
- `ROLES_AND_PERMISSIONS.md` — права `view_products` и `manage_products`;
- `UI_AND_NAVIGATION.md` — списки, техкарта, создание и пользовательская обратная связь;
- `ARCHITECTURE.md` — tenant-изоляция, NestJS, Nuxt, PrimeVue, TanStack Query и OpenAPI;
- `docs/specs/2026-10-12-stage-6-search-and-ingredient-matching-design.md` — готовый поиск компонентов;
- `DEVELOPMENT_PLAN.md` — этап 7.

## Согласованный пользовательский сценарий

1. Сотрудник открывает раздел «Коктейли» в текущем заведении.
2. Список показывает только активные коктейли этого заведения: название, краткий состав и дату изменения. Поиск списка работает по названию.
3. Нажатие на строку открывает отдельную страницу техкарты, чей адрес сохраняется при обновлении и прямом переходе.
4. Пользователь с `manage_products` видит действие «Создать коктейль».
5. Действие открывает форму в Drawer поверх текущего экрана: справа на desktop и во весь экран на телефоне. Отдельного адреса или страницы создания нет.
6. В форме пользователь указывает название, состав, гарниры, технологию, необязательные комментарий и фактический выход.
7. При добавлении компонента поиск показывает глобальные ингредиенты, локальные ингредиенты и заготовки текущего заведения. Если подходящего ингредиента нет, короткая форма создаёт временный локальный ингредиент, после чего он сразу выбран в строке состава.
8. После успешного сохранения Drawer закрывается, данные списка обновляются и пользователь открывает созданную техкарту.
9. Отмена при изменённых данных требует подтверждения потери ввода.

## Экран списка коктейлей

- На desktop используются компактные строки, на телефоне — карточки с тем же набором сведений.
- В списке доступны локальный текстовый поиск и действие создания при наличии права.
- Пустое состояние объясняет, что в заведении ещё нет коктейлей, и показывает доступное действие создания.
- Не создаются неработающие фильтры, сортировки, вкладки, меню или кнопки будущих функций.
- Глобальный каталог не становится отдельным пользовательским разделом.

## Карточка технологической карты

Страница карточки выводит данные в согласованном порядке:

1. название, тип и состояние;
2. состав: компонент, количество и единица;
3. гарниры;
4. технология приготовления;
5. фактический выход, если он указан;
6. комментарий, если он указан.

Ссылки на доступные заготовки и гарниры сохраняют принадлежность текущему заведению. Для первого среза действия редактирования, архива, восстановления, удаления, истории и выгрузки не реализуются.

## Drawer создания коктейля

Форма использует элементы PrimeVue, VeeValidate и Zod. Поля состава добавляются динамически; для каждой строки обязательны компонент, положительное количество и единица. Гарнир выбирается отдельным списком только из гарниров текущего заведения.

Общая ошибка сохранения и ответ сервера показываются в самом верху Drawer, над полями формы. Ошибки конкретных полей показываются рядом с соответствующим полем. При ошибке API введённые данные не пропадают.

Frontend скрывает недоступное действие, но не определяет полномочия самостоятельно. Backend повторно проверяет право `manage_products`, область компании и заведения, допустимость состава, единиц и гарниров.

## Архитектурные границы

- В backend добавляются только недостающие операции: список коктейлей текущего заведения и чтение одной доступной техкарты. Сценарий создания коктейля этапа 5 переиспользуется и меняется только при необходимости фактической формы.
- Контроллеры принимают DTO и передают контекст в прикладной сервис. Они не обращаются к Prisma напрямую.
- Repository-запросы всегда ограничены текущим `venueId`; подмена идентификатора не раскрывает данные другого заведения.
- OpenAPI и API-клиент обновляются штатной генерацией, если контракт меняется.
- Во frontend появляется изолированный модуль `features/cocktails`: список, карточка, Drawer, composable данных и README. Входные страницы остаются тонкими контейнерами.
- TanStack Query обновляет список и карточку после успешного сохранения.
- Существующая CRM-оболочка и её будущая боковая навигация не перерабатываются этим срезом.

## Не входит

- самостоятельные разделы и формы заготовок, гарниров и локальных ингредиентов;
- редактирование коктейля;
- архивирование, восстановление, удаление, аудит в пользовательском интерфейсе и выгрузки;
- общий поиск рабочего пространства, расширенные фильтры, сортировка и сохранение состояния списка в URL;
- новая CRM-оболочка, боковая панель и редизайн существующей навигации;
- новый API или UI для кандидатов сопоставления ингредиентов;
- тестовые файлы, тестовая инфраструктура и тестовые зависимости.

## Критерии готовности

- Пользователь видит только коктейли текущего заведения и может открыть доступную техкарту прямой ссылкой.
- Пользователь с `manage_products` создаёт коктейль в Drawer, используя разрешённые компоненты и гарниры.
- Сценарий поиска и создания временного ингредиента возвращает пользователя к форме с уже выбранной карточкой.
- Ошибки формы понятны, не теряют введённые данные и располагают общую серверную ошибку сверху Drawer.
- После сохранения список и карточка обновляются без перезагрузки страницы.
- В срез не попадают будущие экраны и неработающие элементы интерфейса.
