# Единый умный поиск продукции

## Решение

Все поисковые поля продукции используют единые правила нормализации, сопоставления и ранжирования на сервере. Конкретный экран задаёт разрешённые типы и область данных: списки каталога ограничены типом экрана и текущим заведением, главный поиск может искать все типы, а селектор состава — ингредиенты и заготовки, доступные текущему заведению.

Серверный поиск остаётся на PostgreSQL. Отдельный поисковый сервис не добавляется. Существующая таблица `product_aliases` используется для подтверждённых русских, английских и иных вариантов названия. Нормализованные значения хранятся и обновляются теми же путями, что и исходные названия.

## Диагноз текущего нулевого результата

Проверка локального приложения показала, что для запроса `Водка` база содержит совпадения, а API возвращает страницу с 76 записями. При этом запущенный API отдавал результат в виде массива с одним элементом, тогда как клиент ожидает объект `{ items, totalRecords, categories }`. Клиент читал `items` у массива, получал `undefined` и показывал пустой список. На диске актуальная реализация репозитория возвращает объект, что указывает на устаревший загруженный процесс backend.

Клиент должен проверять форму ответа и показывать ошибку несовместимого ответа вместо ложного состояния «ничего не найдено». Реализация должна подтвердить контракт через работающий API после обновления backend-процесса.

## Правила сопоставления

1. Перед поиском запрос и индексируемые значения приводятся к одной форме: нижний регистр, схлопнутые пробелы, `ё` приравнивается к `е`, диакритика удаляется. Исходное отображаемое название не меняется.
2. Результаты ранжируются в следующем порядке: точное имя, точный подтверждённый алиас, начало имени/алиаса, подстрока имени/алиаса, совпадение слов полнотекстовым поиском, похожее слово/опечатка, затем совпадение атрибутов продукции.
3. Запрос `Апе` должен находить все доступные названия, содержащие эту подстроку после нормализации, а не только начинающиеся с неё.
4. Опечатки ищутся по сходству слов и алиасов, а не только сходству всего длинного поля. Для очень коротких запросов fuzzy-совпадение не применяется; точное, префиксное и подстрочное совпадения остаются доступны.
5. Русское и латинское написание должны находить одну карточку, когда они являются транслитерациями друг друга либо связаны подтверждённым алиасом. Для семантически/орфографически особых названий, например `Апероль` / `Aperol`, используется подтверждённый алиас; обратная транслитерация сама по себе не считается достаточной.
6. Регистр не влияет на результаты. Нормализация применяется одинаково к запросу, именам, алиасам, атрибутам и данным, индексируемым при создании или редактировании продукта.
7. Существующие границы доступа по заведению/компании, ограничение типов для списков, активный статус и сортировка списков сохраняются. Главный поиск показывает только первые 20 результатов без фильтров типа/категории и без пагинации. Поиск не расширяет доступ к данным.

## Область переиспользования

- Главный поиск использует общий поиск без ограничения одним типом и показывает первые 20 результатов в PrimeVue DataTable с одиночным выбором строки; UI-фильтры и пагинация не показываются. В колонке категории для ингредиента показывается человекочитаемое имя его товарной категории из ответа поиска; для коктейля, заготовки и гарнира показывается тип результата. Если категория ингредиента отсутствует, используется подпись «Без категории».
- Списки коктейлей, заготовок и гарниров используют общий поисковый механизм с фиксированным типом текущего экрана. Их текущие фильтры, сортировка и формат ответа сохраняются.
- Селектор ингредиентов в формах коктейлей, заготовок и гарниров ищет активные глобальные ингредиенты и локальные продукты текущего заведения, разрешённые для состава (ингредиенты и заготовки). Новые локальные ингредиенты доступны для поиска сразу после создания.
- Поиск локального продукта по экрану остаётся в текущем заведении; поиск по компании остаётся отдельным разрешённым режимом шеф-бармена.

## Техническое направление PostgreSQL

Использовать текущие `pg_trgm`, полнотекстовые индексы и таблицу алиасов, уточнив условия и ранжирование запросов. Подстроки искать по нормализованным полям оператором `LIKE`/`ILIKE` с экранированным шаблоном и соответствующим trigram-индексом. Для fuzzy-совпадений рассмотреть `word_similarity`/`<%` или эквивалентный оператор для слов/непрерывного фрагмента; пороги и план запроса проверить на реальных данных. Полнотекстовый поиск остаётся отдельным этапом и не заменяет подстрочный поиск.

Официальные источники для реализации:

- PostgreSQL 18 `pg_trgm`: https://www.postgresql.org/docs/18/pgtrgm.html
- PostgreSQL 18 управление полнотекстовым поиском: https://www.postgresql.org/docs/18/textsearch-controls.html
- PostgreSQL 18 сопоставление шаблонов: https://www.postgresql.org/docs/18/functions-matching.html
- Пример сочетания полнотекстового поиска и триграмм: https://github.com/lsaucen/postgres-fulltext-search/blob/main/sql/02_search.sql
- Ещё один набор примеров PostgreSQL FTS: https://github.com/jorzel/postgres-full-text-search/tree/main/src

Примеры из GitHub являются отправной точкой для сравнения, а не готовой реализацией. Разработчик должен проверить актуальные первичные материалы PostgreSQL и выбранные операторы на схеме и данных проекта.

## Не входит в решение

- Внешний поисковый движок или отдельный сервис.
- Автоматическое машинное распознавание переводов и произвольных синонимов.
- Изменение пользовательских названий и их отображения.
- Изменение ролей, областей доступа, состояний каталога и правил состава.
- Изменение аналитики поиска, кроме корректного различения пустого результата и ошибки API.

## Критерии результата

- `Апероль` и `Aperol` приводят к одной карточке при наличии подтверждённой связи вариантов.
- `Апе` находит все доступные карточки с такой подстрокой в названии.
- Изменение регистра, `ё`/`е` и диакритики не меняет ожидаемый набор совпадений.
- Опечатка в названии продукта может найти его по ранжированному fuzzy-совпадению.
- Каждая поисковая поверхность использует общее сопоставление, но сохраняет собственные типы, доступ, фильтры, сортировку и контракт ответа.
- Селектор состава находит как глобальные ингредиенты, так и локальные продукты текущего заведения, доступные в составе.
- Несовпадение формы ответа API показывается как ошибка, а не как нулевой результат.
- До достижения минимальной длины поискового запроса поясняющий текст не выводится; пустая успешная выдача показывается штатным нейтральным PrimeVue `Message` с предложением уточнить запрос.
