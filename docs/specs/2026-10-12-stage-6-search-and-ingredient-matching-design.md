# Спецификация этапа 6: поиск и сопоставление ингредиентов

## Цель

Дать сотруднику быстрый и безопасный поиск доступной продукции, а для временных локальных ингредиентов — контролируемый путь к глобальному каталогу IndieBar. Поиск не должен смешивать данные разных заведений, а автоматическое сопоставление не должно заменять продукт при простом сходстве названий.

## Источники требований

- `PRODUCT_MODEL.md` — поиск, временные локальные ингредиенты и условия автоматической замены;
- `MVP_SCOPE.md` — границы MVP для глобального каталога и поиска;
- `UI_AND_NAVIGATION.md` — области поиска и будущая компоновка рабочего пространства;
- `ARCHITECTURE.md` — PostgreSQL, NestJS, Prisma, BullMQ и server-side tenant-изоляция;
- `DEVELOPMENT_PLAN.md` — область этапа 6.

## Согласованные продуктовые решения

1. Автоматическое сопоставление разрешено только при однозначных основаниях: техническом идентификаторе, полном совпадении бренда, названия и основных характеристик либо заранее подтверждённом алиасе.
2. Похожее название, транслитерация, опечатка или высокий балл релевантности сами по себе не заменяют локальный ингредиент.
3. Неоднозначная или недостаточно описанная локальная позиция продолжает работать без изменений и становится кандидатом для будущего внутреннего backoffice IndieBar.
4. Отдельный центр уведомлений в MVP не создаётся. Значимое автоматическое сопоставление фиксируется в журнале событий.
5. После успешной атомарной замены всех ссылок временный локальный ингредиент удаляется. В обычном каталоге не остаётся скрытых или дублирующих карточек.
6. Полноценная CRM-оболочка, верхняя строка поиска рабочего пространства и пользовательские списки продукции не входят в этап 6. Они будут встроены в утверждённый интерфейс на этапе 7.

## Области поиска

### Поиск компонента

При подборе компонента будущей техкарты сервер возвращает глобальные ингредиенты и локальные продукты только текущего заведения. Данные другого заведения не участвуют ни в выборке, ни в ранжировании.

### Поиск рабочего пространства

Серверная основа поддерживает поиск по доступной продукции текущего заведения: коктейлям, заготовкам, гарнирам и ингредиентам. Поиск по нескольким доступным заведениям возможен только после явного выбора области клиентом и сохраняет принадлежность результата к компании и заведению.

### Сопоставление локальных ингредиентов

Сопоставление не является пользовательским поиском. Фоновая задача ежедневно запускается в 06:00 по московскому времени (`Europe/Moscow`) и обрабатывает новые или изменённые локальные ингредиенты. Она автоматически применяет только однозначное сопоставление; остальные результаты сохраняет как кандидаты для будущей обработки IndieBar.

## Нормализация и ранжирование

Поиск учитывает регистр, лишние пробелы, `е/ё`, диакритические знаки, русский и латинский варианты написания, транслитерацию, алиасы, неполный ввод и опечатки.

Результаты упорядочиваются по убыванию надёжности:

1. точное нормализованное название;
2. подтверждённый алиас;
3. совпадение начала названия;
4. похожее написание;
5. совпадение с учётом бренда, категории, крепости или технического идентификатора.

Ответ API содержит тип найденного продукта и причину совпадения. Ранжирование не наделяет результат правом на автоматическую замену.

## Данные и хранение

PostgreSQL остаётся единственным поисковым хранилищем. В миграции этапа добавляются необходимые расширения и индексы полнотекстового и похожего поиска. Индексы покрывают нормализованные названия, алиасы и данные, нужные для поиска по технологии. Точный механизм представления поискового документа выбирается в детальном плане по официальной документации используемых версий PostgreSQL и Prisma.

Для неоднозначных результатов добавляется отдельная сущность кандидата сопоставления. Она хранит только необходимую для решения связь локального ингредиента с предполагаемой глобальной карточкой, основание сопоставления, уровень уверенности и состояние решения. Пользовательские рецептуры, названия компаний и заведений не становятся частью данных, доступных будущему backoffice без отдельного служебного разрешения.

## Автоматическое сопоставление

Обработка одного локального ингредиента выполняется в транзакции:

1. сервер повторно проверяет текущий статус и принадлежность локальной записи;
2. подтверждает, что найденный глобальный ингредиент всё ещё соответствует строгому правилу;
3. переводит все ссылки текущего заведения на глобальную карточку;
4. создаёт служебное событие журнала;
5. удаляет заменённый локальный ингредиент;
6. завершает транзакцию.

При любой ошибке транзакция отменяется: ссылки и локальная карточка остаются без изменений. Локальная продукция другого заведения никогда не обрабатывается этой операцией.

## API и frontend-границы

Backend получает отдельные прикладные сценарии поиска, обработки кандидатов и атомарной замены. Контроллеры остаются тонкими: принимают DTO, используют существующий контекст компании и заведения и вызывают предметный сервис. Полномочия и принадлежность повторно проверяются внутри прикладного сервиса.

OpenAPI обновляется штатной генерацией, затем генерируется API-клиент. В web-приложении создаются только типизированный слой обращения к поиску и компактный библиотечный элемент выбора ингредиента для будущих продуктовых форм. Временная навигационная оболочка и неработающие элементы интерфейса не расширяются.

## Фоновые задачи

Очередь BullMQ использует идемпотентные задания. Повторный запуск задачи не создаёт дубликаты кандидатов и не выполняет повторную замену уже удалённого локального ингредиента. Планировщик запускает ежедневную обработку в 06:00 в часовом поясе `Europe/Moscow`; повторные попытки определяются в детальном плане с учётом существующего worker-процесса.

## Границы этапа

В этап не входят клиентский backoffice, ручное решение кандидатов, импорт Excel, архив, история в пользовательском интерфейсе, отдельный центр уведомлений, полноценная CRM-оболочка и готовые страницы техкарт. Эти возможности остаются в следующих этапах MVP.

## Критерии готовности

- сервер ищет только в разрешённой пользователю области;
- точный, алиасный, префиксный и нечёткий поиск работают через PostgreSQL-индексы;
- неоднозначность не изменяет локальные данные;
- автоматическая замена допускается только по строгим основаниям и выполняется атомарно;
- после успешной замены локальная карточка удаляется и не засоряет каталог;
- OpenAPI и generated API-клиент соответствуют backend-контракту;
- не создаются тесты, новые тестовые зависимости, временный UI или несогласованные возможности.
