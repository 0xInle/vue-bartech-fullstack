# Быстрые гарниры коктейля — план реализации

> **Для исполнителя:** выполнять задачи последовательно и отмечать их чекбоксами. Дизайн: `docs/specs/2026-10-24-quick-cocktail-garnishes-design.md`.

**Цель:** дать возможность создавать локальные варианты гарнира только с названием из списка гарниров коктейля и сохранять их наряду с гарнирами-техкартами.

**Архитектура:** быстрые варианты используют существующие локальные `ReferenceValue` нового типа `GARNISH`. Для связи с коктейлем добавляется отдельная таблица, чтобы не менять существующую связь с продуктами-техкартами. API сохраняет различие типов; UI показывает варианты вместе и создаёт быстрый вариант в подвале MultiSelect.

**Стек:** Nuxt 4, Vue 3, PrimeVue, TanStack Query, NestJS, PostgreSQL, Prisma, OpenAPI/Orval.

**Дизайн:** `docs/specs/2026-10-24-quick-cocktail-garnishes-design.md`.

## Общие ограничения

- Backend проверяет право `manage_products` и ограничивает быстрые варианты текущим заведением.
- Быстрые варианты содержат только название; составные гарниры сохраняют обязательные состав и технологию.
- Быстрые варианты доступны в селекте коктейля, но не в каталоге техкарт, поиске продуктов и списке гарниров.
- Не запускать тесты, typecheck, dev-сервер или браузер; новые тесты не добавлять без отдельного согласования.
- Форматировать затронутые кодовые и Markdown-файлы Prettier; SQL оформлять по образцу соседних миграций.

## Основные точки риска

1. UUID быстрого варианта может совпасть с UUID продукта, поэтому выбор/API должны передавать тип вместе с id.
2. Нельзя связать коктейль с быстрым вариантом другого заведения или системным значением справочника.
3. Повторяющееся название быстрого варианта в пределах заведения должно возвращать понятный конфликт и оставлять форму открытой.
4. Повторное сохранение/редактирование коктейля должно заменять оба набора связей без потери порядка и выбранных значений.
5. Карточка коктейля, архивная карточка и выгрузка должны отображать быстрые и составные гарниры одинаково по названию.
