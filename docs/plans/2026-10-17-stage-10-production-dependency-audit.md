# План среза этапа 10: проверка production-зависимостей в CI

**Статус:** реализован и прошёл независимое read-only ревью без подтверждённых замечаний.
В `.github/workflows/ci.yml` добавлена команда `pnpm audit --prod --audit-level=critical` сразу
после установки по lockfile. `git diff --check` прошёл. Сам аудит, тесты, typecheck, браузер,
сервер и контейнеры не запускались.

> **Для исполнителей:** после согласования реализовать план ролью `bartech_programmer`, затем
> передать изменения отдельному read-only `bartech_reviewer`. Не создавать тестовые файлы и не
> запускать тесты, typecheck, браузер, сервер или контейнеры без отдельной команды пользователя. Не
> выполнять commit или push. Сохранять все текущие изменения.

**Цель:** блокировать CI при обнаружении критических уязвимостей в production-зависимостях
workspace, сохраняя узкий утверждённый порог из `ARCHITECTURE.md`.

**Требование:** архитектура MVP требует проверять критические уязвимости production-зависимостей в
CI. В корневом проекте зафиксирован `pnpm@11.19.0`; официальный CLI `pnpm audit` поддерживает
`--prod` для production-зависимостей и `--audit-level=critical` для порога проверки:
[документация pnpm 11](https://pnpm.io/11.x/cli/audit).

## Объём

- Добавить `pnpm audit --prod --audit-level=critical` в существующий workflow GitHub Actions после
  установки по lockfile.
- Проверять все workspace production-зависимости, зафиксированные в `pnpm-lock.yaml`.
- Проверка запускается для тех же `push` и `pull_request`, что и текущий CI.
- Уязвимость уровня `critical` должна приводить к неуспешной проверке workflow.
- Ошибка registry или отсутствие доступа к advisory-сервису не должны маскироваться успешным
  завершением; не использовать `--ignore-registry-errors`.
- Не добавлять автоматическое обновление зависимостей, исключения advisory или игнорирование
  unfixed-уязвимостей.
- Если фактический запуск аудита обнаружит критическую уязвимость, проверить её применимость и
  доступный безопасный апдейт. Не применять major-обновление или исключение без отдельного решения;
  сообщить точную находку и остановиться на ней.

## Границы

- Проверяются только production-зависимости; dev-зависимости не входят в требование архитектуры.
- Порог блокировки — `critical`, как указано в `ARCHITECTURE.md`; не повышать его до `high` и не
  менять глобальную конфигурацию аудита.
- Эта проверка не заменяет проверку кода, контейнерных образов, secrets или runtime-конфигурации.
- Не изменять workflow выдачи секретов и не добавлять внешние сервисы безопасности.
- Не запускать тесты, typecheck, браузер, сервер или контейнеры. `pnpm audit` допускается только как
  read-only проверка dependency advisory, если это необходимо для проверки самого нового CI шага.

## Файловые области

- `.github/workflows/ci.yml` — добавить блокирующий шаг проверки критических production advisory
  после установки зависимостей по lockfile.
- `DEVELOPMENT_PLAN.md` — отметить срез после статической проверки и независимого read-only ревью.
- Не менять package версии, lockfile или список игнорируемых advisory без подтверждённой уязвимости
  и отдельного обоснования.

## Критерии готовности

- Workflow запускает аудит для всех production-зависимостей workspace на `push` и `pull_request`.
- `critical` advisory делает workflow неуспешным; низшие уровни не меняют утверждённый порог.
- Ошибки registry не преобразуются в успешный результат.
- Сгенерированные отчёты не содержат секретов, а изменения ограничены CI и документацией.
- Разрешённые проверки: чтение workflow, Prettier для изменённых документов и `git diff --check`.
  Не запускать audit, тесты, typecheck, браузер, сервер или контейнер без отдельной команды
  пользователя.

## Порядок

1. Проверить совместимость флагов с зафиксированной версией pnpm и текущей структурой workspace.
2. Добавить один блокирующий шаг в существующий workflow без автоматического исправления зависимостей.
3. Выполнить разрешённое форматирование и `git diff --check`.
4. Передать пользователю точный отчёт об изменении и непроведённых проверках.
5. Передать workflow на независимое read-only ревью.
6. Отметить срез в `DEVELOPMENT_PLAN.md` после успешного ревью.
