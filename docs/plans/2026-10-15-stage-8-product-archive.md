# План реализации первого среза этапа 8: архив продукции

> **Для агентов-исполнителей:** выполнять задачи последовательно, сохраняя границы ответственности файлов. Новые тесты, тестовую инфраструктуру и тестовые зависимости не создавать без отдельного согласования пользователя.

**Цель:** реализовать единый архив продукции текущего заведения, безопасную архивацию и атомарное восстановление с явным разрешением зависимостей.

**Архитектура:** отдельный модуль `archive` в `@bartech/backend-products` владеет чтением архивных карточек, проверкой зависимостей, архивацией и восстановлением. HTTP-контроллер остаётся тонким адаптером; Nuxt Layer `features/archive` отвечает за список, карточку и подтверждение действий. Существующая блокировка графа заведения сериализует все изменения статуса и состава.

**Технологии:** PostgreSQL, Prisma 7, NestJS 11, OpenAPI, Orval, Nuxt 4, Vue 3, PrimeVue 4, TanStack Query.

**Спецификация:** `docs/specs/2026-10-15-stage-8-product-archive-design.md`

## Глобальные ограничения

- Реализовать только архив и восстановление продукции по спецификации; безвозвратное удаление, экран истории и выгрузки не входят.
- Архивируются только локальные продукты действующего заведения; глобальные ингредиенты не архивируются пользователями.
- Чтение требует `view_archive`, переходы состояния — `manage_product_archive`; сервер проверяет разрешения и `companyId`/`venueId` независимо от frontend.
- Активные зависимости блокируют архивирование; каскадной архивации нет.
- Восстановление и замены связей атомарны; перед записью backend повторно проверяет показанный пользователю план и его подтверждение.
- Генерируемые API-контракт и клиент обновляются только штатной `pnpm api:generate`; сгенерированные файлы вручную не менять.
- Новые автоматические тесты, тестовая инфраструктура и зависимости не создаются; unit-, integration- и e2e-тесты не запускаются.
- Не запускать `typecheck`, dev-сервер, Docker или браузерную проверку без отдельной команды пользователя.
- Форматировать только изменённые файлы через Prettier; не использовать `eslint --fix` как форматтер.
- Сохранять все параллельные пользовательские изменения; не выполнять commit, push или merge без отдельного запроса.

## Фокус ревью

1. Подмена `companyId`, `venueId` или ID карточки не раскрывает архив чужого заведения; проверяется в каждом read/mutation запросе.
2. Архивация под конкурентной записью не пропускает новую активную зависимость между проверкой и сменой статуса; сверяется общий advisory-lock с операциями состава.
3. Архивная карточка не становится доступной для нового выбора компонента, но уже сохранённые исторические ссылки остаются читаемыми.
4. Устаревший план восстановления не принимает изменившийся граф зависимостей, конфликт имени или замену вне разрешённой области; подтверждение пересчитывается сервером.
5. Ошибка в середине восстановления не оставляет частично активированных карточек, замен или `AuditEvent`; все изменения выполняются в одной транзакции.

```text

├── archive-read.service.ts

apps/web/app/
├── features/workspace/components/WorkspaceShell.vue
├── features/archive/README.md
├── features/archive/composables/useProductArchive.ts
├── features/archive/components/ArchiveListScreen.vue
├── features/archive/components/ArchiveCardScreen.vue
├── features/archive/components/ArchiveRestoreDialog.vue
└── pages/app/companies/[companyId]/venues/[venueId]/archive/
    ├── index.vue
    └── [productId].vue
```

`archive-read.*` отвечает за scoped-чтение архива и read-only карточки. `archive-mutation.*`
отвечает только за проверки переходов, подтверждение плана и транзакционные изменения. DTO
публичных HTTP-операций располагаются в `apps/backend`; frontend-состояние и запросы — в
`useProductArchive`; компоненты отвечают каждый за свой экран или диалог.

### Задача 2. Реализовать архивное чтение и архивацию

- Создать: `packages/backend-products/src/archive/archive.dto.ts`

- Изменить: `packages/backend-products/src/products.module.ts`

- Изменить: `apps/backend/src/products/products.controller.ts`
- Изменить: `apps/backend/src/products/products.dto.ts`

**Публичные операции:**

- `GET .../products/archive?query=&type=` — только локальные `ARCHIVED` карточки текущего
  заведения, с поиском по названию и фильтром по допустимому типу; ответ содержит `id`, `type`,
  `name`, `updatedAt`.
- `GET .../products/archive/:productId` — полная read-only карточка архивной продукции с
  компонентами и типовыми полями; чужая, активная, глобальная или отсутствующая карточка даёт
  одинаковый отказ.
- `POST .../products/:productId/archive` — попытка архивации активной локальной карточки.
  Успех возвращает изменённую карточку; при активных зависимостях возвращает известный
  структурированный `409` со списком `{ id, type, name }`, без изменения данных.

- [ ] Реализовать read repository с фильтрами `venueId`, `status = ARCHIVED`, допустимым типом,
  поиском и стабильной сортировкой по названию.
- [ ] Реализовать карточку архива по типам `INGREDIENT`, `PREPARATION`, `GARNISH`, `COCKTAIL`;
  компоненты и справочники читаются только в допустимой области, связи не теряются.
- [ ] В read service повторно проверить `view_archive` через публичный `OrganizationsService`;
  не полагаться только на guard.
- [ ] В mutation service повторно проверить `manage_product_archive`, принадлежность локальной
  карточки текущему заведению и её активный статус.
- [ ] Под общей транзакционной блокировкой заведения найти все активные входящие зависимости:
  `ProductComponent` и `CocktailGarnish`. При наличии зависимостей выбросить типизированный
  конфликт с полным списком активных продуктов; иначе сменить статус и добавить
  `product.archived` в `AuditEvent` атомарно.
- [ ] Подключить модуль через `ProductsModule`, экспортировать только нужные публичные сервисы,
  добавить тонкие контроллерные методы и OpenAPI DTO.

### Задача 3. Реализовать планирование и атомарное восстановление

**Файлы:**

- Изменить: `packages/backend-products/src/archive/archive.dto.ts`
- Изменить: `packages/backend-products/src/archive/archive-read.repository.ts`
- Изменить: `packages/backend-products/src/archive/archive-mutation.repository.ts`
- Изменить: `packages/backend-products/src/archive/archive-mutation.service.ts`
- Изменить: `apps/backend/src/products/products.controller.ts`
- Изменить: `apps/backend/src/products/products.dto.ts`

**Публичные операции:**

- `GET .../products/archive/:productId/restore-plan` — рассчитать дерево архивных зависимостей,
  возможные активные замены, конфликт имени и `confirmationFingerprint`; ничего не записывает.
- `POST .../products/archive/:productId/restore` — принять `confirmationFingerprint`, список
  решений `{ productId, action: RESTORE | REPLACE, replacementProductId? }` и необязательное
  `newName`; возвращать набор успешно восстановленных карточек и выполненных замен.

- [ ] Построить полный граф достижимых архивных компонентов и гарниров; в ответ включать каждую
  карточку один раз, её связь-предок, допустимые активные замены текущего заведения и конфликт
  нормализованного имени.
- [ ] Создавать стабильный отпечаток плана по ID/типу/статусам/связям/конфликту имени и
  предложенным заменам; не включать секретные или ненужные данные карточек.
- [ ] Валидировать действие для каждой архивной зависимости: `RESTORE` либо допустимый
  `REPLACE`; замена доступна только активному продукту правильной области и допустимого типа.
  Обрабатывать цикл и исчезнувший продукт как ошибку всей операции.
- [ ] Если имя занято, принимать `newName` как часть восстановления; нормализовать и проверять
  его теми же правилами уникальности, что применяются при создании/редактировании. При отсутствии
  или конфликте нового имени не записывать изменения.
- [ ] В одной транзакции под общей блокировкой повторно рассчитать план и сравнить fingerprint.
  При изменении плана вернуть свежий структурированный конфликт без записи.
- [ ] Выполнить замену только внутри восстанавливаемых активируемых карточек; восстановить
  выбранное дерево, сохранить все остальные архивные карточки, добавить по событию
  `product.restored` на каждую восстановленную запись. Любая ошибка откатывает статусы, состав,
  названия и аудит.
- [ ] Проверить, что успешный запрос повтора не восстанавливает уже активные записи повторно и
  не создаёт лишние события; вместо этого вернуть безопасный конфликт/актуальное состояние.
