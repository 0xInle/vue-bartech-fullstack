# План реализации среза этапа 9: обращения в поддержку

**Цель:** Реализовать создание и просмотр обращений пользователями, внутреннюю очередь `InternalUser` и безопасную обработку необязательных вложений.

**Архитектура:** `backend-support` владеет обращениями, вложениями, авторизацией и аудитом. Исходные файлы хранятся только в приватном S3-совместимом хранилище и не скачиваются до положительной проверки ClamAV worker. Разрешение `support_requests` ограничивает работу очередью и не открывает клиентскую продукцию.

**Технологии:** NestJS, Prisma, PostgreSQL, BullMQ/Redis, S3-совместимое хранилище, ClamAV, Nuxt/Vue, OpenAPI и сгенерированный API client.

**Спецификация:** `docs/specs/2026-10-16-stage-9-support-requests-design.md`

## Глобальные ограничения

- Создавать обращения могут только авторизованные клиентские пользователи; список клиента фильтруется по текущему `User.id` на backend.
- Внутренняя очередь доступна только `InternalUser` с разрешением `support_requests`.
- Обращение не создаёт `SupportAccessGrant` или `ServiceSession` и не предоставляет доступ к клиентским данным.
- Причины обращения: перенос данных, ошибка или другой вопрос. Статусы: `new`, `in_progress`, `closed`.
- Вложение необязательно; допустимы `xlsx`, `xls`, `csv`, `pdf`, `png`, `jpg`, размер — до 20 МБ на файл.
- Вложение хранится, пока существует обращение; закрытие и удаление/обезличивание аккаунта сами по себе файл не удаляют. У автоматического удаления тикетов и пользовательского удаления обращений нет.
- Пароли, токены, содержимое техкарт и содержимое вложений не попадают в логи. В карантине или до результата ClamAV файл недоступен для скачивания.
- Сохранить все существующие пользовательские незакоммиченные изменения. Не коммитить и не пушить.
- Не создавать тестовые файлы/инфраструктуру и не запускать тесты, typecheck, браузер, локальный сервер или контейнеры.

## Задачи

### 1. Модели обращений и вложений

- Добавить модели обращений, вложений, сканирования и transactional outbox. Состояния файла различают как минимум ожидающий сканирования, чистый и отклонённый результат.
- Связать автора с `User`, необязательные компанию и заведение — только валидной tenant-парой, ответственного — с `InternalUser`.
- Сохранить обращение и задание сканирования в одной транзакции. Файл и метаданные не удаляются при закрытии обращения или обезличивании автора.
- Создать миграцию без изменений существующих аккаунтных и продуктовых данных.

### 2. Сервис и клиентский API

- Реализовать создание обращения, выбор только доступного пользователю контекста, список собственных обращений и чтение своего обращения.
- Не включать в технический context пароли, токены и данные/содержимое продуктовых карточек; ограничить и безопасно нормализовать данные браузера и error id.
- Ограничить upload до 20 МБ; разрешать только перечисленные расширения и фактические типы содержимого.
- Писать объект только в приватную область quarantine со случайным server-generated key. Клиент не выбирает object key и не получает прямой доступ к объекту.
- Отдавать краткоживущую ссылку скачивания только после `CLEAN` и повторной проверки автора либо внутреннего permission.

### 3. Сканирование вложений

- Передавать задачи через transactional outbox и BullMQ с идемпотентностью повторной доставки.
- Worker читает quarantine object потоково, передаёт ClamAV командой/клиентом, который выбран на основании официальной документации, и фиксирует результат.
- Только чистый объект переходит в доступное состояние. Неподдерживаемый, заражённый или не прошедший сканирование объект не скачивается; безопасная категория ошибки возвращается UI без раскрытия scanner internals.
- Повторная обработка не создаёт дубликатов и не позволяет устаревшему результату изменить уже актуальное состояние файла.
- При удалении обращения в будущем удалять связанный объект и metadata атомарно/повторяемо; автоматическое удаление по сроку в этом срезе не добавлять.

### 4. Внутренняя очередь и аудит

- Защитить все endpoints очереди отдельным `InternalSessionGuard` и проверкой `support_requests`.
- Добавить фильтр/пагинацию очереди в рамках существующих API conventions, деталь обращения, назначение активного `InternalUser`, смену статуса.
- Повторно проверять permission на каждом запросе и скачивании; контекст обращения не даёт перехода к клиентским продуктам.
- Записывать создание обращения (системное/клиентское событие по принятому audit pattern), назначение и изменение статуса во внутренний аудит, не сохраняя message/file content в audit metadata.

### 5. HTTP, API client и web

- Подключить только необходимые routes. Multipart не логируется; middleware redaction и Problem Details не раскрывают содержимое файла или scanner error.
- Экспортировать OpenAPI и сгенерировать API client штатной командой.
- Сделать пользовательский экран помощи: причина, сообщение, необязательное вложение, отправка и список собственных обращений со статусами/состоянием сканирования.
- Сделать внутренний список и экран обработки; скрывать все функции от `User`, а очередь — от `InternalUser` без `support_requests`.
- Не добавлять чат, email-уведомления, выдачу доступа и просмотр клиентской продукции.

### 6. Инфраструктура и документация

- Отдельный DevOps исполнитель добавляет локальный ClamAV daemon в Compose и сверяет образ/параметры с официальной документацией; scanner порт не публикуется на внешние интерфейсы.
- Программист подключает backend/worker config, S3 quarantine и scanner integration по утверждённому контракту.
- Обновить README новых пакетов, OpenAPI/client и `DEVELOPMENT_PLAN.md` после завершения.
- Форматировать только затронутые файлы Prettier; допускаются targeted lint/build, если область понятна. Запрещённые пользователем проверки не запускать.

## Приоритеты read-only ревью

- Tenant spoofing при указании компании/заведения и чтении пользовательского списка.
- Multipart превышает лимит через transfer encoding, неверный MIME/расширение или дублированные поля.
- Ни одна ошибка, retry, гонка или потеря worker не открывает quarantine объект до `CLEAN`.
- Параллельный/повторный scan не может откатить актуальное состояние или обработать другой object key.
- `support_requests` не превращается в разрешение на `SupportAccessGrant` или продуктовый контент.
- Удаление/обезличивание `User` и ограничения внешнего S3 не оставляют доступный клиенту сиротский объект.

Этот план требует подтверждения. Реализацию приложения передать `bartech_programmer`;
изменение Compose и выбор ClamAV deployment config — отдельная порученная часть
`bartech_devops`, если пользователь подтвердит такой способ. По завершении обоих исполнителей
передать результат на отдельное read-only ревью. Тесты, typecheck, браузер, сервер и
контейнеры остаются запрещены прямым указанием пользователя.
