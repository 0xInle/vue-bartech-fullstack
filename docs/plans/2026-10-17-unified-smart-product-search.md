# Единый умный поиск продукции — план реализации

> Реализовать после согласования этой спецификации. Сохранить все ранее существовавшие изменения в рабочем дереве.

**Цель:** исправить фактическое отображение нулевой выдачи и обеспечить одинаковые правила поиска по продукции на всех поисковых экранах.

**Спецификация:** `docs/specs/2026-10-17-unified-smart-product-search-design.md`.

## Ограничения

- Не менять продуктовые правила доступа и видимость активных/архивных записей.
- Не заменять PostgreSQL внешним поисковым сервисом.
- Сохранить server-side фильтры, фасеты и пагинацию главного поиска.
- Сохранить типовые ограничения и контракты списков.
- Не затрагивать `packages/database/src/index.js` и несвязанные изменения рабочего дерева.
- Не создавать тестовые файлы или тестовую инфраструктуру и не запускать автоматические тесты без прямого разрешения. В этой задаче пользователь прямо запросил тщательную проверку поиска, поэтому допускается ручная проверка текущего API/браузерного потока после реализации без запуска тестового набора.
- Не запускать `typecheck`. Форматирование затронутых файлов и статические lint/build проверки разрешены.

## Задача 1. Зафиксировать runtime-контракт и причины нулевого состояния

**Область:** `apps/web/app/features/products/composables/useWorkspaceProductSearch.ts`, API DTO/контроллеры и `packages/backend-products/src/search/`.

- [ ] Убедиться, что оба постраничных endpoint возвращают ровно объект `{ items, totalRecords, categories }`, а `scope=COMPONENT` сохраняет прежний массивный контракт.
- [ ] Добавить проверку формы ответа на клиенте; некорректная форма должна приводить к явному состоянию ошибки, не к пустому массиву.
- [ ] Проследить текущий запрос от компонента ввода через debounce, query key, сгенерированный API client и DTO до SQL и обратно, включая отмену устаревшего запроса.
- [ ] Обновить backend-процесс/сборку способом, предусмотренным текущим dev workflow, и повторить тот же запрос через работающий API. Не маскировать несовпадающий контракт адаптацией к случайной форме массива.

## Задача 2. Проверить PostgreSQL-подход и индексируемые поля

**Область:** `packages/backend-products/src/search/`, Prisma schema и миграции базы.

- [ ] Сверить выбранные операторы с актуальной документацией PostgreSQL 18, в частности `pg_trgm`, `word_similarity`, операторы подстрочного поиска и полнотекстовый поиск.
- [ ] Проверить текущие миграции, индексы, все функции записи/обновления нормализованных полей и подтверждённых алиасов.
- [ ] Подтвердить, какие поля индексируются отдельно: имя, алиас, атрибуты ингредиента/категории, технология и состав.
- [ ] Оценить подстрочные шаблоны для 3-символьного запроса и корректное экранирование `%`/`_`; короткие запросы не должны вызывать fuzzy-шума.
- [ ] Сопоставить по крайней мере два GitHub-примера PostgreSQL FTS + trigram с официальной документацией и записать в итог краткие выводы и ссылки.

## Задача 3. Реализовать единые правила поиска

**Область:** общий backend search/rules/repository, запись поисковых полей и aliases, при необходимости миграция.

- [ ] Реализовать общий нормализатор и единое ранжирование: exact name, exact alias, prefix, substring, FTS, fuzzy-word, product attributes.
- [ ] Поиск подстроки применять к имени продукта и подтверждённым алиасам; если документация обещает поиск по атрибутам, сохранять и для них согласованное подстрочное поведение.
- [ ] Обеспечить сопоставление русской/латинской формы через нормализованные варианты и подтверждённые алиасы. Проверить присутствие связи для `Апероль` / `Aperol` в используемых данных; при отсутствии добавить её способом, согласованным с моделью `product_aliases`, без выдуманной машинной «переводческой» логики.
- [ ] Проверить, что создание и изменение коктейлей, заготовок, гарниров, ингредиентов и aliases обновляет все поля/индексы, участвующие в поиске.
- [ ] Сохранить parameterized SQL и серверную фильтрацию по venue/company/type/status; исключить расширение доступа через пользовательские параметры.

## Задача 4. Подключить общий поиск к поверхностям

**Область:** `packages/backend-products/src/cocktails/`, `preparations/`, `garnishes/`, `search/`, API DTO/клиенты и `apps/web/app/features/products/`.

- [ ] Главный поиск использует общее сопоставление, не меняя страницу, facets, сортировку релевантности и визуальные состояния.
- [ ] Списки коктейлей, заготовок и гарниров передают общий поисковый query с фиксированным типом экрана; сохранить текущие категорийные фильтры и сортировку `name`/`updated`.
- [ ] Поиск в списках остаётся ограничен активными продуктами выбранного заведения.
- [ ] Селектор состава ищет по локальным активным ингредиентам и заготовкам текущего заведения плюс доступным глобальным ингредиентам; локальный компонент должен появляться после сохранения.
- [ ] Сохранить типы для внутренних сессий поддержки/каталога, если они используют те же точки выбора; проверить их область и существующий scope до подключения.
- [ ] Не изменять несвязанные экраны и аналитику.

## Задача 5. Форматирование и проверка

- [ ] Отформатировать только затронутые файлы через `pnpm exec prettier --write <пути>`.
- [ ] Запустить lint/build только затронутых workspace, если их область изменений однозначна.
- [ ] Провести ручную проверку через API и интерфейс для: `Апероль`, `Aperol`, `Апе`, варианта с опечаткой, верхнего/нижнего регистра, `ё`/`е`, локального ингредиента, глобального ингредиента, типа/категории и страницы списка.
- [ ] Проверить, что некорректная форма API показывает ошибку; пустой результат остаётся отдельным состоянием.
- [ ] Не запускать тесты, typecheck или создавать тестовую инфраструктуру.
- [ ] Просмотреть полный diff и проверить неизменность посторонних пользовательских файлов.

## Задача 6. Независимое ревью

- [ ] Передать готовое изменение агенту `bartech_reviewer` только для чтения.
- [ ] Попросить проверить PostgreSQL-запросы/индексы, Unicode и транслитерацию, алиасы, поисковые области, права доступа, форму ответа, актуальность сгенерированного клиента и отсутствие несвязанных изменений.
- [ ] Внести только подтверждённые замечания и передать их на повторное ревью.
