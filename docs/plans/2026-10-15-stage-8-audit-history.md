# План реализации журнала действий

> **Для исполнителя:** выполнять задачи строго по порядку и отмечать чекбоксы. План реализует [спецификацию журнала действий](../specs/2026-10-15-stage-8-audit-history.md); продуктовые правила спецификации не переопределять.

**Цель:** обеспечить аудит значимых действий, защищённое серверное чтение истории и пользовательский экран с фильтрами и переходом из карточки.

**Архитектура:** запись события остаётся частью предметной операции в её backend-пакете. Чтение истории и единая модель ответа принадлежат новому предметному пакету `@bartech/backend-audit`, уже предусмотренному `ARCHITECTURE.md`; пакет повторно проверяет доступ через публичный API организаций. HTTP-контроллер остаётся в `apps/backend`, интерфейс — в отдельной Nuxt feature.

**Стек:** pnpm workspace, NestJS, Prisma, OpenAPI/Orval API-клиент, Nuxt 4, Vue 3, PrimeVue.

**Спецификация:** `docs/specs/2026-10-15-stage-8-audit-history.md`

## Общие ограничения

- Сервер повторно подтверждает членство, область компании/заведения и право на каждом чтении.
- Участник без `view_history` видит только собственные действия с продукцией и адресованные ему события выдачи/отзыва прав.
- Сотрудник с `view_history` видит только полную область, подтверждённую его актуальным членством и ролью.
- События изменения данных записываются в той же транзакции, что и бизнес-операция; ошибка записи аудита отменяет операцию.
- В журнал не записываются секреты, токены, старый состав или текст прежней версии карточки.
- Не добавлять новые роли/права, аналитику просмотров, экспорт, откат версий или несуществующие клиентские сценарии.
- Не создавать/запускать тесты, не добавлять тестовую инфраструктуру или зависимости, не запускать typecheck и не проверять браузер без отдельного разрешения пользователя.
- Generated API-клиент обновлять только командой `pnpm api:generate` после изменения DTO/контроллера; generated-файлы вручную не редактировать.
- Перед изменениями проверить состояние рабочей копии и сохранить все параллельные пользовательские изменения.

## Файлы и границы ответственности

- `packages/backend-audit/` — новый предметный пакет: авторизованный запрос, фильтры, DTO ответа, репозиторий чтения и публичный NestJS API.
- `packages/backend-organizations/src/team/team.service.ts` — устойчивый ID субъекта событий изменения роли, делегированных прав и временной ответственности.
- `packages/backend-products/src/products.service.ts`, `packages/backend-products/src/products.repository.ts` и предметные update-сервисы — события успешного создания/изменения; перед правками сверить все пути записи продуктов.
- `packages/backend-organizations/src/organization-invitations.service.ts` и другие обнаруженные producer-ы — менять только при подтверждённом пробеле, не дублировать события.
- `apps/backend/src/audit/` — HTTP DTO и контроллер истории; подключить в модуле композиции API согласно текущей структуре приложения.
- `apps/backend/package.json` — зависимость от `@bartech/backend-audit`, если backend импортирует его NestJS-модуль напрямую.
- `packages/api-client/openapi.json`, `packages/api-client/src/generated/` — результат генерации API, не редактировать вручную.
- `apps/web/app/features/history/` — feature списка истории и composable API.
- `apps/web/app/pages/app/companies/[companyId]/venues/[venueId]/history/index.vue` — тонкий маршрут истории.
- Карточки коктейля, заготовки и гарнира — переход к истории с фильтром по сущности в существующих меню действий.

## Области повышенного риска

1. Подмена `companyId`, `venueId`, `actorId` или ID сущности: чтение остаётся в подтверждённом сервером scope; фильтры только сужают результат.
2. Бармен/старший бармен пытается читать чужие действия: доступны только его собственные продуктовые события и адресованные ему события прав.
3. Удаление членства и обезличивание аккаунта: аудит сохраняется, бывшему сотруднику не открывается история, а для разрешённой истории остаётся безопасное отображение автора.
4. Успешное изменение без события либо событие для отклонённой операции: запись атомарна с изменением данных.
5. Одинаковые временные отметки и длинная история: стабильный порядок `createdAt DESC, id DESC` и ограниченная постраничная выдача.

## Разрешённые статические проверки

- `pnpm lint` или целевые `pnpm --filter <package> lint` для изменённых пакетов;
- `pnpm --filter <package> build` для изменённых backend-пакетов и `pnpm --filter @bartech/web build`;
- `pnpm api:generate` при изменении публичного API;
- `pnpm exec prettier --write <изменённые файлы>` и `git diff --check`.

Не запускать агрегированную `pnpm verify`: она включает `typecheck` и другие проверки, не разрешённые для этой задачи.
