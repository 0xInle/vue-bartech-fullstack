# План реализации первого среза этапа 9: вход `InternalUser`

**Цель:** Реализовать отдельный вход внутренних сотрудников IndieBar с паролем, обязательным TOTP, первичной настройкой, восстановлением по одноразовым кодам и операторским сбросом MFA.

**Архитектура:** Backend остаётся единственным источником состояния и полномочий. Внутренние аккаунты, challenge и сессии изолируются от клиентского identity-контура; UI `/internal` вызывает отдельный API и не получает доступ к клиентским данным. Одноразовые операции и replay-защита фиксируются атомарно в PostgreSQL, кратковременные ограничения запросов используют существующую инфраструктуру проекта.

**Технологии:** NestJS, Prisma, PostgreSQL, Redis, Nuxt/Vue, существующий API client, Argon2id, TOTP по RFC 6238, AES-256-GCM.

**Спецификация:** `docs/specs/2026-10-16-stage-9-internal-user-authentication-design.md`

## Границы и ограничения

- Реализуется только первый срез входа `InternalUser`; функции backoffice, доступ к клиентским данным и `SupportAccessGrant` не добавляются.
- Клиентские `User`, их сессии, cookie и сценарии входа не меняются.
- Требования к TOTP replay-защите, восстановлению и попыткам берутся из спецификации; новые глобальные правила не вводятся.
- Не создавать тестовые файлы или тестовую инфраструктуру и не запускать тесты, typecheck либо браузерные проверки.
- Не запускать сервер, контейнеры, не коммитить и не отправлять изменения.
- Сохранять все исходные пользовательские изменения в рабочем дереве.

## Области файлов

- `packages/database/prisma/identity.prisma`, `packages/database/prisma/database.prisma`, новая миграция в `packages/database/prisma/migrations/`: отдельные сущности внутренних пользователей, сессий, challenge, recovery-кодов и аудита; индексы, ограничения и связи.
- `packages/backend-identity/src/internal-auth/` (новые файлы), `packages/backend-identity/src/index.ts`, `packages/backend-identity/src/auth/identity.module.ts`: внутренний сервис, DTO, контроллер/guard, криптографическая и rate-limit логика, операторские команды; не расширять клиентский `SessionGuard`.
- `apps/backend/src/app.module.ts`, `apps/backend/src/http/`: подключение маршрутов и redaction секретов/токенов по принятым в проекте правилам.
- `.env.example`: отдельный обязательный ключ шифрования TOTP и его описание; не переиспользовать `OUTBOX_ENCRYPTION_KEY`.
- `apps/web/app/pages/internal/` и `apps/web/app/features/internal-auth/` (новые файлы): вход, ввод TOTP, первичная настройка, показ recovery-кодов, восстановление и повторная привязка; только маршруты и данные этого среза.
- `packages/api-client`: обновлённая OpenAPI-спецификация и сгенерированный клиент для новых внутренних маршрутов, используя принятый в репозитории процесс генерации.
- `DEVELOPMENT_PLAN.md`, профильные README пакетов: отметить согласование спецификации и реализацию среза после завершения; описать новые границы пакета.

## Точки проверки

Реализация должна обеспечивать следующие проверяемые инварианты. Автоматические проверки по ним не запускаются в этой задаче по прямому ограничению пользователя.

- Пароль сам по себе не создаёт внутреннюю сессию; клиентская сессия и cookie не принимаются внутренними маршрутами.
- Повтор одного принятого TOTP временного шага невозможен атомарно для параллельных запросов и разных challenge.
- Пять проверок на один challenge резервируются атомарно; 100 последовательных неверных TOTP-кодов на аккаунт отключают только TOTP-аутентификатор, который затем можно восстановить recovery-кодом и перепривязкой.
- Setup-token и recovery-код одноразовые; recovery-код принимается только один раз при конкурентных запросах.
- Ошибки не раскрывают существование аккаунта; нет жёсткой блокировки аккаунта по одному email.
- Неудачи ограничиваются на источнике и challenge; учёт ошибок аккаунта ограничивает частоту, но не блокирует корректную попытку.
- Recovery отзывает прежние внутренние сессии, требует настройки нового TOTP и аннулирует все прежние recovery-коды.
- Потеря устройства вместе со всеми recovery-кодами требует операторского сброса после ручной проверки; операция аудируется.
- Секреты и коды не попадают в журналы; секрет TOTP зашифрован отдельным ключом.
- Внутренние маршруты не раскрывают клиентские данные и новые функции backoffice.

## Последовательность работ

### 1. Схема данных и криптографические примитивы

- Добавить отдельные модели `InternalUser`, `InternalSession`, `InternalAuthChallenge`, `InternalRecoveryCode` и `InternalAuditEvent` либо эквивалентные модели, сохраняя изоляцию от `User` и `AuditEvent`.
- Добавить состояния аккаунта, типы и ограничения согласно спецификации; уникальность email, хеша токена, потребления OTP time-step и recovery-кодов должна поддерживаться БД там, где применимо.
- Создать миграцию без изменения данных существующей клиентской аутентификации.
- Реализовать внутренние helpers для случайных токенов, хеширования одноразовых секретов, TOTP, шифрования TOTP-секрета AES-256-GCM и безопасного сравнения.
- Добавить конфигурацию отдельного TOTP encryption key, проверяемую конфигурацией backend.

### 2. Сервис внутренней аутентификации и операторские операции

- Реализовать контролируемое создание `PENDING_ENROLLMENT` и одноразового setup-token, а также операторский сброс MFA; никакого публичного создания аккаунтов.
- Реализовать настройку пароля/TOTP без выдачи сессии до успешного подтверждения TOTP; после активации показать десять recovery-кодов один раз.
- Реализовать двухшаговый вход, внутренние сессии, отдельную cookie и guard, текущую сессию, завершение текущей и всех внутренних сессий.
- Реализовать повторное использование TOTP-защиту через атомарное compare-and-set аккаунтного последнего принятого временного шага и общий счётчик последовательных неудач; после 100 неудач отключать только фактор, оставляя recovery-путь по recovery-коду.
- Реализовать восстановление по паролю и recovery-коду в транзакции: однократное потребление кода, отзыв сессий, ограниченное состояние и настройка нового TOTP.
- Встроить ограничения попыток по источнику, challenge и аккаунту без жёсткой блокировки аккаунта по email; ошибки входа остаются неразличимыми по существованию аккаунта.
- Добавить события внутреннего аудита для создания/отключения, настройки факторов, восстановления, сброса и отзыва сессий; не сохранять секреты.
- Сделать внутренние API DTO и ошибки согласованными с backend API-контрактом.

### 3. HTTP-интеграция и контракт API

- Подключить внутренний auth-контроллер отдельно от клиентского identity-контроллера.
- Закрыть защищённые маршруты только отдельным `InternalSessionGuard`; реализовать CSRF и cookie с атрибутами из архитектуры, используя отдельное имя.
- Убедиться, что редактирование URL/логов исключает setup, recovery, TOTP и сессионные секреты.
- Обновить OpenAPI и сгенерированный API client штатным способом репозитория.

### 4. Интерфейс `/internal`

- Добавить отдельные экраны входа (пароль → TOTP), первичной настройки, однократного показа recovery-кодов, восстановления и повторной настройки.
- Состояния интерфейса выводить только из ответов внутреннего API; не хранить секреты дольше необходимого и не помещать их в URL, localStorage или журналы.
- Обеспечить нейтральные ошибки входа и понятные сообщения об истечении/исчерпании конкретного challenge.
- Не добавлять навигацию и функции backoffice за пределами входа.

### 5. Документация и статические проверки

- Обновить README `backend-identity` и документацию auth UI, а также актуальный статус и следующий шаг в `DEVELOPMENT_PLAN.md`.
- Передать изменённые файлы Prettier только если их форматирование требуется правилами проекта; выполнять лишь для затронутых файлов.
- Разрешены lint/build только при условии, что области команд понятны и не затрагивают чужие изменения. По прямому указанию пользователя не запускать тесты, typecheck, браузерные проверки, локальный сервер или контейнеры.
- Передать краткий фактический отчёт: итог, изменённые файлы, выполненные и невыполненные проверки, замечания и следующий шаг.

## Вопросы для независимого ревью

- Могут ли гонки, повторные запросы или транзакционные повторы обойти атомарную защиту TOTP/recovery?
- Нельзя ли через вход, настройку или восстановление обойти требование пароля и TOTP либо получить клиентский контекст?
- Не приводит ли account rate-limit к блокировке аккаунта злоумышленником или к обходу ограничений при смене challenge/IP?
- Все ли секреты, QR-содержимое, коды и токены исключены из логов, ошибок, URL и клиентского постоянного хранилища?
- Не затронуты ли существующие схемы, API и сценарии `User`?
