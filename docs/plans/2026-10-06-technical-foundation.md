# Технический фундамент IndieBar — план реализации

> **Для агента-исполнителя:** выполнять пункты последовательно и отмечать чекбоксы по мере завершения. Тесты, тестовые библиотеки и тестовую инфраструктуру не создавать и не запускать без отдельного прямого разрешения пользователя.

**Цель:** создать чистый `pnpm`-monorepo с запускаемыми Nuxt и NestJS приложениями, локальными инфраструктурными сервисами и типизированным клиентом служебного API.

**Архитектура:** одно Nuxt-приложение обслуживает публичные страницы и основу PWA; отдельное NestJS-приложение предоставляет REST API и отдельную точку запуска worker-процесса. Общие технические пакеты содержат Prisma-схему и генерируемый Orval API-клиент. Предметные модули, регистрация, пользователи и рабочие экраны в этот этап не входят.

**Стек:** pnpm workspaces, актуальные стабильные Node.js LTS, Nuxt 4, Vue 3, TypeScript, PrimeVue 4, Tailwind CSS, TanStack Query, VeeValidate, Zod, NestJS 11 с Express, Prisma, PostgreSQL, Redis, BullMQ, Pino, OpenAPI, Orval, Docker Compose, GitHub Actions.

**Спецификация:** `ARCHITECTURE.md`; объём и порядок этапа — раздел «Этап 1. Технический фундамент monorepo» в `DEVELOPMENT_PLAN.md`.

## Глобальные ограничения

- Использовать только актуальные стабильные версии, сверенные с официальной документацией при реализации; фиксировать разрешённые версии в `pnpm-lock.yaml` и Docker-образах.
- Не добавлять Supabase, Pinia, микросервисы, Nx, Turborepo, GraphQL, Kubernetes, тестовую инфраструктуру или зависимости.
- Не включать бизнес-логику регистрации, пользователей, компаний, заведений, сотрудников и продуктов.
- Не добавлять фиктивные слои предметной области или пустые пакеты только ради заранее предполагаемого роста.
- Backend остаётся модульным монолитом; frontend Layers остаются частью одного Nuxt-приложения.
- Секреты и реальные `.env` файлы не хранятся в Git; для локальной разработки предоставляются только безопасные примеры.
- Не изменять продуктовую модель или глобальную архитектуру без отдельного согласования.
- Не создавать и не запускать тесты. Разрешены только `lint`, `typecheck`, `format`, Prisma schema validation, генерация/проверка OpenAPI-клиента и `build`.
- Все пользовательские тексты пишутся на русском языке; код и машинные идентификаторы — на английском.

## Файловая карта

```text
pnpm-workspace.yaml              # пакеты workspace
package.json                     # корневые команды и закреплённый менеджер пакетов
pnpm-lock.yaml                   # единый lock-файл
.npmrc                           # настройки pnpm
.node-version                    # версия Node.js для локальной разработки и CI
.editorconfig                    # общие правила редактора
eslint.config.mjs                # общие правила ESLint для Vue/TypeScript
.prettierrc.json                 # общие правила форматирования
apps/
  web/                           # Nuxt 4, публичная стартовая страница и оболочка приложения
  backend/                       # HTTP API на NestJS и точка входа worker
packages/
  database/                      # схема Prisma, Prisma client и миграции
  api-client/                    # настройки Orval и сгенерированный API-клиент
tooling/                         # только фактически используемые общие настройки
infrastructure/
  compose.yaml                   # PostgreSQL, Redis и Mailpit для разработки
.github/workflows/ci.yml         # статические проверки без тестов
```

`packages/backend-*` создаются в тех этапах, где появляются соответствующие доменные модули. Nuxt Layers добавляются вместе с первыми предметными разделами, а не как пустые каталоги.

## На что обратить внимание

- **Повторяемая установка зависимостей:** версии package manager, Node.js и пакетов согласованы между локальной средой и CI; frozen install не изменяет lock-файл.
- **Публикация OpenAPI:** спецификация и Orval-клиент воспроизводимо генерируются из единого backend-контракта; CI умеет обнаружить рассинхронизацию.
- **Локальные сервисы и секреты:** Compose стартует с документированными безопасными локальными значениями, а секреты production не попадают в репозиторий.
- **Разделение процессов:** HTTP API и worker имеют отдельные точки входа и могут собираться и запускаться раздельно.
- **Служебные ошибки и проверка готовности:** liveness не маскирует отказ критичных зависимостей; readiness проверяет только нужные для HTTP-сервиса зависимости.

### Задача 3. NestJS HTTP API и worker entrypoint

**Файлы:**

- Создать: `apps/backend/package.json`, конфигурацию Nest CLI/TypeScript, `src/main.ts`, `src/worker.ts`, `src/app.module.ts`.
- Создать: технические файлы middleware/filters/interceptors, модули `health` и `meta`, конфигурацию OpenAPI и Pino.
- Создать: схему безопасной валидации переменных окружения и `.env.example` без настоящих секретов.

**Результат и интерфейсы:**

- `main.ts` запускает HTTP API с глобальной валидацией, `/api/v1`, `requestId`, Pino и единым Problem Details.
- `worker.ts` запускает самостоятельный Nest application context для фоновых обработчиков; HTTP listener не поднимается в worker-процессе.
- Служебный endpoint `/api/v1/health/live` сообщает только о живом процессе; `/api/v1/health/ready` проверяет соединение с обязательной PostgreSQL и Redis.
- Минимальный endpoint `/api/v1/meta` предоставляет безопасный пример DTO для документации OpenAPI и генерации API-клиента.
- Ошибки не выдают stack trace, SQL, секреты и персональные данные.

## Критерий готовности

Этап завершён, когда все команды из задачи 6 проходят, web и backend запускаются как раздельные процессы одного workspace, worker собирается отдельно, OpenAPI-клиент и Prisma схема воспроизводимы, локальные PostgreSQL/Redis/Mailpit доступны через документированные команды, а параметры dev-бакета Yandex Object Storage документированы. Реальная отправка объектов проверяется после реализации `FileStorage`.

При обнаружении расхождения между этим планом и `ARCHITECTURE.md` реализацию соответствующей части остановить и сначала согласовать правку документа. Успешная сборка не является подтверждением бизнес-корректности; продуктовые сценарии начнутся на этапе 2.
