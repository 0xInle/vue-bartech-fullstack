# План реализации первого среза этапа 8: выгрузки продукции

> **Для агента-исполнителя:** выполнять задачи последовательно. Сохранять все существующие и параллельные изменения, не очищать и не откатывать незнакомые файлы. Новых сабагентов не создавать.

**Цель:** реализовать три вида выгрузки продукции через единый фоновый поток: PDF одной техкарты, ZIP с PDF выбранных техкарт и структурированный ZIP выбранного заведения.

**Спецификация:** `docs/specs/2026-10-15-stage-8-product-exports-design.md`.

**Граница:** этот план покрывает самостоятельную подсистему экспорта текущего заведения. По ранее согласованному порядку интеграция с закрытием — следующий отдельный срез этапа 8; контракт для него уже описан в спецификации, но данный план не создаёт сценарии закрытия и не выдаёт постзакрывающие ссылки. Этап 8 нельзя помечать завершённым после этого плана: остаётся интеграция закрытия и другие незавершённые пункты общего плана.

**Архитектура:** предметный пакет `@bartech/backend-exports` владеет запросами, аудитом, фоновой подготовкой и форматами. `@bartech/backend-products` предоставляет узкий публичный API для scoped-снимка продукции. `@bartech/backend-files` реализует `FileStorage` и S3-адаптер. HTTP- и worker-модули `apps/backend` связывают пакеты. Существующий `OutboxMessage` предназначен для email и не переиспользуется; для экспорта создаётся отдельная транзакционная запись доставки. Публичный контракт остаётся в OpenAPI, клиент обновляется только штатным генератором.

**Технологии:** NestJS 11, PostgreSQL, Prisma 7, Redis/BullMQ 6, Nuxt 4, Vue 3, TanStack Query, S3 API Yandex Object Storage. Для интеграции SDK, подписи URL и библиотек PDF/ZIP сверять API и ограничения с первичной документацией актуальных совместимых версий; конкретные прямые зависимости фиксировать только в тех workspace, где они используются.

## Ограничения исполнения

- Не создавать тестовые файлы, тестовую инфраструктуру и тестовые зависимости. Не запускать unit-, integration- и e2e-тесты.
- Не запускать `typecheck`, dev-серверы, Docker, браузер или визуальную проверку.
- Разрешённые проверки этого плана: Prettier только для затронутых файлов, `git diff --check`, Prisma validate, lint затронутых workspace и штатная `pnpm api:generate` для OpenAPI/Orval. Штатная генерация API не заменяет отдельный typecheck.
- Не выполнять commit, push, reset, clean или иные действия, отменяющие существующие незакоммиченные изменения.
- Не менять утверждённые бизнес-правила, разрешения, границы компании/заведения, срок файла 24 часа и срок ссылки 5 минут.
- PDF по отдельной карточке создаётся для рецептурных техкарт коктейля, заготовки и гарнира. Ингредиенты остаются данными состава и резервного JSON, отдельная PDF-карточка ингредиента не добавляется.
- Обычные запросы и ссылки требуют действующего `export_data` и текущей области. Исключение для файла потока закрытия не реализуется в этом срезе.

**Файлы:** `packages/database/prisma/exports.prisma`, `packages/database/prisma/schema.prisma`, новая миграция в `packages/database/prisma/migrations/`, `packages/database/src/index.ts` при необходимости экспорта enum/типов, раздел `ExportRequest` в `DATA_MODEL.md`.

- [ ] Добавить сущность запроса с автором, компанией, заведением, форматом/видом выгрузки, нормализованными параметрами, состоянием `QUEUED | PROCESSING | READY | FAILED`, временем создания/начала/готовности/истечения, ограниченным числом попыток, lease обработки, ключом объекта, MIME-типом, размером и безопасным кодом ошибки.
- [ ] Добавить отдельную запись export-outbox, связанную с запросом и уникальную для доставки этого запроса. Создание запроса, этой записи и `AuditEvent(export.requested)` выполнять одной транзакцией.
- [ ] Не хранить бинарные данные в PostgreSQL. Не добавлять в request/outbox секреты S3, подписанные URL или полные данные рецепта.
- [ ] Задать каскады и индексы так, чтобы обычные временные запросы не ослабляли текущую изоляцию tenant-данных. Постзакрывающее хранение не проектировать в этой миграции.
- [ ] Подготовить миграцию, которая добавляет таблицы/индексы без удаления или пересоздания текущих таблиц и данных. Сверить Prisma-модель с SQL.

### Задача 4. Реализовать жизненный цикл фоновой выгрузки

**Файлы:** `packages/backend-exports/src/export.repository.ts`, `export.service.ts`, `export-outbox.repository.ts`, `export.processor.ts`, `export.module.ts`, `export-worker.module.ts`, `export-cleanup.service.ts`, `packages/backend-exports/src/index.ts`, `apps/backend/src/worker.module.ts`.

- [ ] Создание запроса повторно проверяет `export_data`, актуальное членство, `companyId`/`venueId`, доступность каждой выбранной карточки и допустимость архивных карточек; в очередь передаётся только ID запроса. `export_data` не расширяет доступ к архиву: дополнительно проверяется уже согласованное `view_archive`.
- [ ] Реализовать диспетчеризацию export-outbox в BullMQ, устойчивую к повторной доставке и падению между `queue.add` и отметкой записи. Не менять email-only `OutboxMessage` и его processor.
- [ ] Worker атомарно захватывает `QUEUED` запрос либо восстанавливает `PROCESSING` запрос с истёкшим lease. Он строит результат через product snapshot API, загружает объект в `FileStorage`, затем транзакционно переводит запрос в `READY` и записывает `export.completed`.
- [ ] Повтор BullMQ job не создаёт второй логический файл и не добавляет дублирующее аудит-событие. Использовать детерминированный ключ по ID запроса и условные переходы состояния.
- [ ] Настроить конечный сквозной предел обработки от времени создания и ограниченное число попыток. При исчерпании попыток или истечении общего срока переводить запрос в `FAILED`, записывать `export.failed` с безопасной категорией, не выдавать частичный объект и позволять новый запрос. Удалять возможный orphan-object идемпотентно.
- [ ] Очистка удаляет готовые файлы и request/outbox-метаданные по истечении 24 часов от `completedAt`; для ошибки срок файла не применяется, а технические метаданные ошибки очищаются после короткого диагностического срока, выбранного в конфигурации без пользовательской истории. Очистка идемпотентна и выдерживает повторный запуск.
- [ ] Worker завершает BullMQ/Redis соединения при остановке приложения. Логи содержат только ID запроса, тип задачи и безопасную категорию ошибки.

## Фокус независимого ревью

1. Tenant-изоляция на всех этапах: создание, чтение статуса, выбор карточек, S3-объект, подпись ссылки, очистка и аудит.
2. Проверка разрешения `export_data` выполняется на backend; Chef/Bar Manager и делегированный сотрудник не получают scope шире `PermissionService`.
3. Отмена/повтор Outbox и BullMQ не теряет задание и не создаёт повторный объект/аудит; зависшее задание гарантированно достигает ошибки по общему deadline.
4. Выгрузка резервной копии содержит только утверждённую продукцию, корректно сохраняет локальные зависимости и снимки используемых глобальных ингредиентов; в неё не попадают команда, приглашения, аудит или аккаунты.
