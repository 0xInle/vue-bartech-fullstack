# План среза этапа 10: состояние отсутствия сети и блокировка изменений

**Статус:** реализован и прошёл независимое read-only ревью без подтверждённых замечаний.

**Проверки:** Prettier, web lint, web build и `git diff --check` прошли. Сборка завершилась
успешно с предупреждением Rollup о комментарии в собранном Vue-файле. Тесты, typecheck, браузер,
сервер и runtime-проверки не запускались.

> **Для исполнителей:** после согласования реализовать план ролью `bartech_programmer`, затем
> передать изменения отдельному read-only `bartech_reviewer`. Не создавать тестовые файлы и не
> запускать тесты, typecheck, браузер, сервер или контейнеры без отдельной команды пользователя. Не
> выполнять commit или push. Сохранять все текущие изменения.

**Цель:** постоянно показывать состояние отсутствия сети и не отправлять изменяющие API-запросы,
пока браузер не сообщил о восстановлении соединения.

**Архитектура:** общий клиентский composable отслеживает `navigator.onLine` через события `online` и
`offline`, безопасно начиная работу только после гидрации. Глобальный баннер сообщает об отсутствии
сети. Центральная обёртка API блокирует запросы с методом, отличным от `GET`, `HEAD` и `OPTIONS`, до
вызова `fetch`; чтение и повторные GET-запросы остаются доступными. Все web API-запросы должны пройти
через `useApiFetch`, поэтому защита стоит на общей транспортной границе, а не дублируется по формам.

**Технологии:** Nuxt 4, Vue 3, браузерные события `online`/`offline`, общий `useApiFetch`.

**Источники:** `MVP_SCOPE.md` («Устройства и PWA»), `ARCHITECTURE.md` («PWA»),
`UI_AND_NAVIGATION.md` («PWA»), `DEVELOPMENT_PLAN.md` (этап 10),
`apps/web/app/composables/useApiFetch.ts` и `apps/web/app/app.vue`.

## Глобальные ограничения

- Офлайн-чтение бизнес-данных, офлайн-очередь, локальная база и разрешение конфликтов не добавляются.
- Не кешировать API-ответы, продукцию, пользовательские данные или страницы с данными компаний.
- При отсутствии сети изменяющий запрос не должен достигать `fetch`; после события `online` запросы
  снова разрешены.
- Первоначальное состояние должно быть SSR-безопасным и не вызывать несовпадение гидрации.
- Сохранять текущие изменения; не выполнять commit или push.
- Не создавать тестовые файлы и не запускать тесты, typecheck, браузер, сервер или контейнеры без
  отдельной команды пользователя.

## Поведение

- После клиентской гидрации читать `navigator.onLine` и подписываться на `window` events `offline` и
  `online`; при размонтировании удалять слушатели.
- При `offline` показывать глобальный постоянный баннер с сообщением, что просмотр и изменения требуют
  подключения. При `online` убирать баннер.
- В `useApiFetch` определять HTTP-метод без учёта регистра; отсутствующий метод считать `GET`.
- При `navigator.onLine === false` отклонять изменяющий запрос до `globalThis.fetch` понятной
  русскоязычной ошибкой. Не блокировать `GET`, `HEAD` и `OPTIONS`.
- Не использовать Service Worker или browser storage для сохранения бизнес-ответов.

## Фокус независимого ревью

- Изменяющие запросы блокируются до отправки, а `GET`, `HEAD` и `OPTIONS` не блокируются.
- HTTP-метод определяется корректно для всех форм `RequestInfo`.
- Cookie, credentials, headers и signal остаются неизменными для разрешённого запроса.
- Сетевой баннер отражает `navigator.onLine`, не мигает из-за SSR-гидрации и снимает слушатели.
- Service Worker и транспорт не начинают кешировать ответы API или бизнес-данные.
