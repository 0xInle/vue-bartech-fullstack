# План декомпозиции backend-сервисов IndieBar

> **Для агентов-исполнителей:** реализовывать этот план можно только после подтверждения пользователем и выбранного им способа исполнения. План использует флажки `- [ ]` для отслеживания.

**Цель:** разделить backend-сервисы, которые смешивают независимые сценарии, сохранив поведение MVP, публичные API и утверждённые архитектурные границы.

**Архитектура:** модульный монолит NestJS с предметными пакетами. Сначала составляется карта обязанностей и зависимостей, затем внутренние границы уточняются в `backend-identity` и `backend-organizations`. Межпакетная зависимость допускается только однонаправленная через публичный API; циклы запрещены.

**Технологии:** NestJS 11, TypeScript, Prisma, PostgreSQL, pnpm workspaces, ESLint, Prettier.

**Спецификация:** `docs/specs/2026-10-09-backend-service-structure.md`.

## Глобальные ограничения

- `ARCHITECTURE.md` задаёт глобальные технические границы; новые бизнес-правила не добавляются.
- Сохраняются HTTP-маршруты, форматы запросов/ответов и OpenAPI-контракт.
- Сохраняются полномочия, tenant-изоляция, транзакционные границы, блокировки, аудит и Outbox.
- Backend-пакеты могут зависеть друг от друга только ациклично и через публичные экспорты; `apps/*` не импортируются из пакетов.
- Не добавлять новые тесты, тестовые зависимости и не запускать тесты без отдельной прямой команды пользователя.
- Разрешены точечные `lint`, `typecheck`, `format` и `build` для затронутых пакетов и приложения.
- Prettier — единственный форматтер; форматировать только изменённые файлы.
- Не выполнять коммиты, не менять продуктовые документы и не расширять объём работ без необходимости и согласования.
- После работы сообщить пользователю перечень изменённых файлов и реально выполненные статические проверки.

## Области ревью

1. Регистрация, подтверждение email, вход и восстановление пароля сохраняют прежние ограничения и ответы.
2. Принятие приглашения сохраняет атомарность членства и аккаунта, проверки владельца ссылки, срок действия и правила повторного использования.
3. Вызовы в рамках одной операции сохраняют единую транзакцию и блокировки; разделение не оставляет промежуточных частичных состояний.
4. Пакетные зависимости остаются однонаправленными, проходят через публичный API и не становятся скрытыми циклическими вызовами провайдеров NestJS.
5. Worker очистки истёкших данных продолжает вызывать те же правила очистки и не смешивает очистку с доставкой почты.

- [x] Перенести каждый связный сценарий в отдельный именованный provider, не вводя универсальный фасад, лишние интерфейсы или копии бизнес-правил.

- [x] Сценарии принятия приглашения, создающие/связывающие пользовательский аккаунт, оставить на identity-стороне с явным вызовом публичного API организаций.
- [x] Заменить потребителей общего `IdentityService` на узкие сценарные providers; `IdentityController` остаётся тонкой HTTP-границей.
- [x] Если очистка требует собственного провайдера, сделать worker зависимым только от него; не связывать очистку срока хранения с отправкой писем.
- [x] Экспортировать из `IdentityModule` и package entrypoint только типы и провайдеры, действительно используемые другими пакетами или `apps/backend`.
- [x] Удалить прежний общий `IdentityService`, если после миграции он стал лишь pass-through фасадом; не сохранять его ради совместимости внутри монорепозитория.
- [x] Сохранить результат регистрации, формат сессий/cookie, приглашения, проверку email и атомарность существующих операций.

**Критерий задачи:** каждый новый provider отвечает за связный пользовательский сценарий, контроллеры не зависят от большого общего сервиса, обратная зависимость организаций на identity не появляется.

## Ожидаемый результат

- Регистрация, аутентификация/сессии, принятие приглашения и очистка имеют читаемые границы ответственности.
- Работа с организациями, рабочими пространствами, командой и приглашениями не сосредоточена в одном сервисе на сотни строк.
- Изменённые сервисы не являются универсальными посредниками между контроллерами и логикой.
- Публичные HTTP/OpenAPI-контракты и поведение приложения не меняются.
- Цельные небольшие сервисы не переписываются «за компанию».
- Тесты не создаются и не запускаются без прямого разрешения.
