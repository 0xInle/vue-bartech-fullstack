# План среза этапа 8: выгрузка в сценариях закрытия

## Цель

Связать существующую фоновую выгрузку с уже реализованными сценариями закрытия заведения и компании. Пользователь выбирает выгрузку или явно продолжает без неё; выбранная выгрузка связывается только с конкретной операцией закрытия. После закрытия инициатор может получить новую краткоживущую ссылку только на готовый файл этой операции и только до его исходного срока истечения.

## Источники и утверждённые решения

- `DOCUMENTATION_MAP.md` — приоритет продуктовых, MVP, модельных, UI и архитектурных документов.
- `DEVELOPMENT_PLAN.md`, этап 8 — самостоятельные выгрузки уже реализованы; интеграция с закрытием остаётся отдельным обязательным срезом.
- `docs/specs/2026-10-15-stage-8-product-exports-design.md` — форматы, состав и поток интеграции.
- `docs/plans/2026-10-15-stage-8-product-exports.md` — границы первого среза экспорта.
- `docs/plans/2026-10-16-stage-4-company-venue-lifecycle.md` — реализованные операции закрытия и граница между этапами.
- `COMPANY_AND_VENUE_LIFECYCLE.md`, `ROLES_AND_PERMISSIONS.md`, `MVP_SCOPE.md`, `UI_AND_NAVIGATION.md` — бизнес-права, подтверждение точным названием, последствия и пользовательские переходы.
- Решения пользователя: только данные продукции; единая фоновая система; сначала самостоятельная выгрузка, затем отдельная интеграция с закрытием; файл хранится 24 часа от готовности, ссылка — до 5 минут; инициатор после закрытия получает доступ только к файлу, явно созданному для этой операции; пароль повторно не запрашивается, подтверждение — точное название сущности.

## Границы среза

- Не менять самостоятельные сценарии PDF одной карточки, ZIP выбранных карточек и резервного ZIP заведения, кроме повторного использования их сервисов и общей авторизации.
- Для закрытия заведения дождаться готовности выбранной выгрузки до окончательного подтверждения либо выполнить подтверждённое пользователем закрытие без выгрузки.
- Для закрытия компании разрешить шеф-бармену подготовить экспорт до начала 168-часового ожидания либо во время него. Экспорт компании — один ZIP, содержащий раздельные резервные ZIP всех заведений, доступных этому шеф-бармену; каждый внутренний пакет содержит только данные продукции и собственный манифест.
- Внутри одной операции можно сохранять связь только с выгрузками, явно запрошенными из её пользовательского потока. Обычные ранее созданные запросы не получают постзакрывающий доступ автоматически.
- При закрытии исходной области сохранять метаданные и объект готовой закрывающей выгрузки только до исходного `expiresAt` (24 часа от готовности). Закрытие не продлевает срок.
- После закрытия использовать отдельный аутентифицированный путь, ограниченный инициатором, идентификатором операции и конкретным экспортом. Он не возвращает доступ к рабочему пространству, другим файлам, API компании/заведения или созданию новых выгрузок.
- При отмене закрытия компании операция становится отменённой. Её экспорт не получает исключительный доступ к удалённой области; пока область активна, применяются обычные правила доступа. Не вводить новые сроки или историю файлов.
- Закрывающие запросы, которые к моменту закрытия не готовы, не становятся доступными после закрытия. Их обработка отменяется/очищается по существующему идемпотентному purge-процессу; физическое удаление области не продлевается ожиданием выгрузки.
- Не менять правила поддержки, полномочия, срок хранения или состав файлов; не добавлять импорт, командные данные или сведения аккаунтов.

## Текущее состояние кода

- `ProductExportRequest` требует `companyId` и `venueId` и каскадно удаляется вместе с ними.
- Текущие типы экспорта — `SINGLE_PDF`, `BATCH_PDF_ZIP`, `VENUE_BACKUP_ZIP`; обработчик читает один снимок заведения.
- Обычные endpoint-ы статуса и скачивания требуют действующее рабочее пространство и `export_data`.
- Сервис закрытия заведения и worker окончательного закрытия компании каскадно удаляют исходные области и ставят запросы экспорта на purge. Существующий `ProductExportCleanup` повторяет удаление и не подходит для готового файла, разрешённого к скачиванию после закрытия.
- Экран закрытия сейчас только ссылается на самостоятельный раздел выгрузок; выбор, ожидание готовности и результат закрытия с доступом к файлу ещё не связаны.

## Реализация

### 1. Идентификатор операции закрытия и долговечность выбранного файла

- Добавить минимальную сущность операции закрытия, создаваемую сервером, с непрозрачным UUID, инициатором, типом операции, текущим статусом и исходной областью, пока та существует. Связи с компанией и заведением должны обнуляться при их удалении, а запись должна переживать каскад ровно настолько, насколько требуется связанному готовому файлу.
- Связать запросы экспорта с операцией закрытия отдельным nullable FK/отношением. Для закрывающего запроса сохранить автора, исходную область для аудита, формат, параметры, статус, `completedAt`, исходный `expiresAt` и ключ объекта. Не использовать повторно удаляемую компанию/заведение как единственное доказательство доступа.
- Для незакрывающих запросов сохранить существующую политику каскадной очистки и tombstone-повторы. Существующие связи компаний/заведений сделать nullable только если это необходимо для переживания каскада; обычные endpoint-ы должны отказывать, когда текущая область уже отсутствует.
- При финализации закрытия атомарно связать выбранный готовый запрос с операцией и audit event. Если пользователь выбрал «без выгрузки», операция не получает файлового исключения.
- После срока `expiresAt` удалить объект, связанные метаданные запроса и запись операции, когда у операции больше нет живых файлов. Успешное закрытие не создаёт бессрочного хранения.
- Не помечать готовый, неистёкший запрос, уже связанный с операцией, обычным scope-purge. Все неготовые, истёкшие и обычные запросы продолжают проходить через существующий безопасный purge.

### 2. Тип и формирование экспорта компании

- Добавить тип `COMPANY_CLOSURE_BACKUP_ZIP`, который принимает только серверный снимок области компании шеф-бармена и перечень её действующих заведений; не принимать список `venueId` от клиента как источник полномочий.
- Зафиксировать в параметрах запроса проверенный список заведений на момент создания и создать соответствующую запись в Export Outbox одной транзакцией.
- Через публичную границу `backend-products` прочитать обычный резервный снимок каждого выбранного заведения. Использовать уже существующий renderer для внутренних `VENUE_BACKUP_ZIP`; не дублировать формат карточек или JSON.
- Сформировать внешний ZIP со стабильными отдельными путями для каждого заведения и общим версионированным манифестом. Внутренние резервные ZIP остаются раздельными и содержат собственные манифесты. Не добавлять пользователей, роли, приглашения, аудит или аккаунты.
- Сохранять идемпотентность по существующим request id/attempt key, безопасное временное хранение, отказ без публикации частичного результата и аудит `export.requested`/завершения.

### 3. Серверный поток закрытия

- Расширить lifecycle API для создания/получения операции и запроса экспорта в её контексте; проверять автора, роль, состояние компании/заведения, область и существующее `export_data` до постановки задачи.
- Для закрытия заведения разрешать финальное закрытие с `exportRequestId` только когда запрос готов, не истёк, принадлежит инициатору, создан для этой операции и ровно этой пары company/venue. В той же транзакции повторно проверить имя, полномочия, состояние и связь, создать/связать аудит и закрыть заведение. Без `exportRequestId` требовать отдельный явный выбор без выгрузки.
- Для компании создать операцию подготовки до запуска 168-часового срока, если пользователь выбрал экспорт; связать запрос заранее. Разрешить создание связанной выгрузки также по действующей операции в период ожидания. Запуск закрытия и переход компании в `PENDING_CLOSURE` остаются атомарными и требуют точного названия; пароль не запрашивать.
- До срока закрытия выгрузки компании проверять роль шеф-бармена и актуальное право читать всю компанию; закрывающие запросы обычного менеджера не могут расширить его область.
- При отмене компании пометить операцию отменённой и убрать её исключительный доступ. На финализации после дедлайна сохранить только готовые, неистёкшие файлы, связанные с операцией; остальные запросы поставить на идемпотентный purge, затем удалить компанию.
- Добавить защищённый endpoint чтения статуса/ссылки по операции после закрытия. Он требует активную учётную сессию именно автора, завершённую операцию, связь с запросом, статус `READY` и `expiresAt > now`; выдаёт подписанную ссылку максимум на 5 минут и не расширяет область.
- Обычные export endpoint-ы и их авторизация остаются без изменений по смыслу и не получают post-closure exception.

### 4. Интерфейс

- Заменить простой переход из `OrganizationLifecyclePanel.vue` на выбор выгрузки в контексте закрытия: поддерживаемые варианты из существующей подсистемы, прогресс, ошибка, готовый файл и явное действие продолжить без выгрузки.
- Закрытие заведения блокируется до готовности выбранного файла; отмена диалога не запускает закрытие. Перед необратимым действием повторно показывать последствия и требовать точное название заведения.
- В сценарии закрытия компании дать подготовить общий ZIP до запуска ожидания либо из плашки активной операции в течение 168 часов. Экран точно показывает исходный дедлайн и срок файла; подготовка не продлевает срок компании или файла.
- После закрытия заведения показать страницу/состояние результата с идентификатором только этой операции и ссылкой на связанный файл, если он ещё не истёк. После окончательного удаления компании тот же доступ доступен по сохранённому маршруту операции. При отсутствии выбранного файла показать обычное завершение без ссылки.
- Не хранить export id в общем пользовательском recent history, не показывать прочие выгрузки после закрытия и не восстанавливать меню рабочей области.
- Сохранить работу для обычного бар-менеджера только в собственных заведениях, для шеф-бармена — в пределах компании по документированным правилам.

## Критерии готовности

- Выбранный файл связан с операцией закрытия на backend; обычная выгрузка не получает исключения после закрытия.
- Venue close не может завершиться до готовности связанного файла; явный сценарий без него остаётся доступен.
- Company closure ZIP включает только продукты действующих заведений в разрешённой шеф-бармену области, без командных и аккаунтных данных.
- После закрытия только авторизованный инициатор может скачать связанный, готовый и неистёкший файл; невозможно получить новый export, другой файл или данные закрытой области.
- `expiresAt` остаётся исходным сроком 24 часа от готовности; закрытие не продлевает срок. Подписанная ссылка не превышает 5 минут.
- Транзакции закрытия сохраняют корректный audit event и не теряют готовый объект из-за обычного scope purge; отмена/ошибка/истечение приводят к безопасной очистке.
- Ещё действуют правила «точное название, без повторного пароля», области доступа и срок ожидания 168 часов.

## Результат реализации

Реализованы операции подготовки закрытия заведения и компании, привязка единственной явно запрошенной выгрузки к операции, общий ZIP продукции действующих заведений компании, аутентифицированный маршрут результата операции и повторяемая очистка файла после истечения срока. Для закрытия заведения требуется готовый выбранный файл либо явное продолжение без выгрузки. Для закрытия компании выгрузку можно подготовить до запуска ожидания и в течение срока ожидания; точное название остаётся подтверждением закрытия. После удаления области доступ к файлу сохраняется только у инициатора операции и до исходного `expiresAt`.

Очистка экспортного объекта, не завершившаяся из-за ошибки хранилища, сохраняет запись очистки и повторяется существующим процессом. Метаданные закрывающего запроса и операция удаляются после подтверждённого удаления файла. Пользователь подтвердил этот вариант для ошибок удаления.

Проверки реализации: `prisma:generate`, `prisma:validate`, штатная генерация API, сборки `backend-exports`, `backend` и `web`, `git diff --check`. Тесты, typecheck, браузер, сервер, Docker и worker не запускались. Этап 8 в целом не отмечен завершённым; требуется независимое read-only ревью.
