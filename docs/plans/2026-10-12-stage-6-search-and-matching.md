# План реализации этапа 6: поиск и сопоставление ингредиентов

**Статус:** реализация завершена, статические проверки пройдены; независимое ревью ожидается.

## Цель

Дать приложению быстрый поиск продукции в разрешённой области текущего заведения и безопасную фоновую обработку временных локальных ингредиентов. Автоматическая замена допускается только при однозначном основании; после успешного переназначения ссылок локальная карточка удаляется в той же транзакции.

## Зафиксированные границы

- Поиск получает только глобальные ингредиенты и локальную продукцию запрошенного заведения. Проверка области выполняется до поиска и повторно в прикладном сервисе.
- Ранжирование учитывает точное совпадение, подтверждённый алиас, префикс, похожее написание, русскую/латинскую запись и атрибуты. Оно не даёт права автоматически менять продукт.
- Автоматическое сопоставление разрешено только по уникальному техническому идентификатору, точному совпадению бренда, названия и основных характеристик либо по подтверждённому алиасу.
- Неоднозначный и недостаточно описанный ингредиент остаётся рабочей локальной карточкой. Для будущего backoffice сохраняется кандидат, но пользовательский экран его обработки сейчас не создаётся.
- Успешная замена в одной транзакции переводит все ссылки текущего заведения на глобальный ингредиент, фиксирует `AuditEvent` и удаляет локальную карточку. Ошибка отменяет всю транзакцию.
- Worker запускает ежедневную идемпотентную задачу ровно в 06:00 в зоне `Europe/Moscow`. HTTP-процесс не создаёт worker и не планирует задачу.
- В этап не входят CRM-оболочка, глобальная строка поиска, страницы продукции, ручная обработка кандидатов, backoffice, архив, импорт и уведомления.
- Новые тесты, тестовая инфраструктура и зависимости не создаются. Unit-, integration-, e2e-тесты, `typecheck`, dev-сервер и браузерная проверка не запускаются без отдельной команды пользователя.

Названия каталогов фиксируют ответственность: `search` только находит и ранжирует доступную продукцию; `matching` только принимает решение о сопоставлении и выполняет атомарную замену; `worker` в приложении связывает предметный сценарий с BullMQ. Существующие `ProductsService` и `ProductsRepository` не должны разрастаться поисковой и фоновой логикой.

## Задачи и порядок

### 1. Расширить данные и безопасно применить миграцию

- В `packages/database/prisma/products.prisma` добавить признак подтверждённости алиаса и отдельную сущность кандидата сопоставления с состоянием, основанием, уровнем уверенности, идентификаторами локальной и предполагаемой глобальной карточек и техническими датами.
- Кандидат не хранит названия компаний, заведений, рецептуры или персональные данные. Его связь с локальной карточкой не должна мешать удалить карточку при успешной автоматической замене.
- Создать отдельную Prisma-миграцию для `pg_trgm`, полнотекстовых и trigram-индексов по нормализованным названиям и подтверждённым алиасам. После независимого ревью расширения поиска оформляются следующей миграцией; уже применяемые миграции не переписывать.
- Не менять существующие идентификаторы и seed-контракт глобального каталога. Все алиасы, загружаемые из контролируемого глобального JSON, считаются подтверждёнными; существующие алиасы переводятся в такое состояние миграцией.
- Для транслитерации и диакритики не создавать неиндексируемую выборку всей таблицы: нормализатор строит ограниченный набор вариантов запроса, а repository выполняет параметризованный запрос только по индексируемым полям.

**Проверка:** `pnpm prisma:validate`, генерация Prisma Client и ручной просмотр миграционного SQL. Миграцию на локальной базе не применять без отдельной команды пользователя.

### 2. Выделить предметный поиск продукции

- В `search/product-search-rules.ts` вынести чистую нормализацию поискового текста: пробелы, регистр, `е/ё`, диакритика и детерминированные русско-латинские варианты. Длина и пустой ввод валидируются до обращения к базе.
- В `search/product-search.repository.ts` реализовать только scoped-запросы: глобальные ингредиенты и активная локальная продукция конкретного `venueId`. Запрос возвращает минимальные поля для будущего выбора компонента: идентификатор, тип, название, область, данные ингредиента и причину совпадения.
- Поиск рабочего пространства также индексируемо учитывает характеристики ингредиентов, технологию составного продукта и состав через компоненты только из глобального каталога либо того же заведения. Поисковые значения атрибутов и технологии нормализуются при записи, для них создаются отдельные индексы.
- Применить ранжирование в порядке: точное нормализованное название, подтверждённый алиас, префикс, похожее написание, совпадение с учётом категории, бренда, крепости или технического идентификатора. Лимит результата и минимальная длина нечёткого запроса задаются сервером, а не клиентом.
- В `search/product-search.service.ts` повторно проверить `view_products` через публичный API организаций и вызвать repository. Он не получает доверенный `venueId` без контекста пользователя.
- Заменить точечный сценарий `findGlobalIngredients` на единый поиск, сохранив API узким: поиск компонента отдаёт глобальные ингредиенты и доступные локальные позиции, а поиск рабочего пространства принимает явное ограничение типов. Полный пользовательский интерфейс списков не добавлять.

**Проверка:** lint изменённых backend workspace и просмотр запросов на отсутствие выборки без `venueId` или ограничения глобальным каталогом.

### 3. Реализовать строгие кандидаты и атомарную замену

- В `matching/ingredient-match-rules.ts` отделить поиск кандидатов от разрешения на автоматическое действие. Высокий балл похожести сам по себе никогда не возвращает разрешение на замену.
- В `matching/ingredient-matching.repository.ts` добавить операции чтения локальных ингредиентов, поиска глобальных кандидатов, upsert кандидата, обновления `ProductComponent`, записи `AuditEvent` и удаления локального продукта. Все операции транзакционной замены принимают `Prisma.TransactionClient`.
- В `matching/ingredient-matching.service.ts` реализовать два сценария: обработку одного локального ингредиента и пакетный запуск обработки. Перед заменой сервис заново читает исходную локальную карточку и глобальный кандидат в транзакции, чтобы не опираться на устаревший результат очереди.
- Строгие основания для автоматической замены:
  1. ровно один глобальный ингредиент с тем же непустым `externalIdentifier`;
  2. ровно один глобальный ингредиент с идентичными нормализованными названием и брендом, категорией и всеми указанными основными характеристиками;
  3. ровно один глобальный ингредиент с подтверждённым алиасом, если остальные заданные характеристики не противоречат карточке.
- При замене обновить ссылки `ProductComponent` только текущего заведения, создать `AuditEvent` с типом системного автоматического сопоставления и минимальными техническими идентификаторами, затем удалить локальную карточку. Кандидат для уже удалённой карточки не оставлять.
- При нуле, нескольких или противоречивых кандидатах не менять продукцию, а идемпотентно создать либо обновить кандидат для будущего backoffice. Повторная задача не создаёт дубликаты.

**Проверка:** статический просмотр транзакции: обновления ссылок, аудит и удаление происходят в одном callback Prisma; запросы не используют данные другого заведения.

### 4. Подключить ежедневный worker

- В `apps/backend/src/worker/ingredient-matching.processor.ts` создать очередь и worker BullMQ рядом с интеграционным кодом приложения, используя существующие `REDIS_URL`, Pino и жизненный цикл NestJS.
- В `onModuleInit` worker-процесса зарегистрировать scheduler через `upsertJobScheduler` с постоянным идентификатором, cron-паттерном `0 0 6 * * *` и `tz: "Europe/Moscow"`. Повторная инициализация обновляет, а не дублирует расписание.
- У задания задать ограниченное число попыток, нарастающую задержку и очищение завершённых/старых ошибочных задач по существующему подходу очередей. Обработчик должен спокойно завершаться, если задание доставлено повторно или локальная карточка уже удалена.
- Добавить `IngredientMatchingWorkerModule` только в `WorkerModule`; не импортировать его в `AppModule`. Обновить README проекта и пакета продукции: в production worker обязателен как отдельный процесс, локально его запускают отдельно командой `pnpm run dev:worker` только когда требуется проверить фоновые задачи.

**Проверка:** `pnpm --filter @bartech/backend build:worker` и lint затронутого backend-кода. Не запускать worker или Docker без отдельной команды пользователя.

### 5. Опубликовать контракт и минимальный web-слой

- В `apps/backend/src/products/products.dto.ts` описать query и response поиска, включая тип продукта и причину совпадения, без служебных полей кандидатов.
- В контроллере оставить тонкий защищённый маршрут в текущем контексте компании и заведения. Guard проверяет вход, предметный сервис повторяет полномочия и область.
- Сгенерировать OpenAPI и `packages/api-client` только командой `pnpm api:generate`; generated-файлы не редактировать вручную.
- Создать в `apps/web/app/features/products/` только типизированный composable поиска и компактный PrimeVue-компонент выбора ингредиента. Он использует сгенерированный API-клиент, debounce/отмену устаревших запросов и не добавляет маршрут, временную навигацию или новый экран. Компонент должен быть готов к прямому включению в форму этапа 7, а не имитировать несуществующую страницу.
- Добавить `README.md` feature-модуля и обновить README `backend-products`: ответственность файлов, tenant-границы, порядок генерации API и отдельный worker.

**Проверка:** `pnpm api:generate`, lint затронутых workspace, форматирование только изменённых файлов и `git diff --check`. Не запускать `typecheck`, тесты, браузер или dev-сервер.

## Не входит

- Ручное решение кандидатов, экран backoffice и создание глобальной карточки из кандидата.
- Экран списка продукции, карточки, полноценный поиск в CRM-оболочке и формы техкарт.
- Уведомления пользователям об автоматическом сопоставлении.
- Архивирование, восстановление, выгрузки и пользовательский журнал аудита.
- Изменение ролей, приглашений, инфраструктуры Docker или существующей seed-структуры каталога.

## Критерии готовности

- Поиск отдаёт только доступные глобальные ингредиенты и локальную продукцию текущего заведения.
- Типовые точные, алиасные, префиксные и нечёткие запросы используют PostgreSQL-индексы, не загружая каталог в память приложения.
- Нечёткое совпадение не запускает автоматическую замену.
- Автоматическая замена всегда атомарна, изолирована текущим заведением, создаёт аудит и удаляет заменённую локальную карточку.
- Неоднозначные результаты не меняют данные и не дублируют кандидатов при повторе задачи.
- Задание ежедневно планируется на 06:00 `Europe/Moscow` только отдельным worker-процессом.
- OpenAPI и generated API-клиент соответствуют backend-контракту; интерфейс не получает неработающих экранов или навигации.

## Фактический результат реализации

- Prisma-схема прошла `pnpm prisma:validate`; Prisma Client сгенерирован через `pnpm prisma:generate`.
- Контракт OpenAPI и API-клиент обновлены через `pnpm api:generate`.
- Lint backend-модулей продукции, backend-приложения и web-приложения пройден; worker собран.
- `git diff --check` пройден. Тесты, `typecheck`, локальная миграция, worker runtime, сервер, Docker и браузерная проверка не запускались согласно ограничениям этапа.
- Ручное независимое ревью ещё не выполнено.

## Фокус независимого ревью

1. Tenant-изоляция поиска, создания кандидата и переназначения ссылок.
2. Невозможность автоматической замены по одной похожести названия.
3. Откат ссылок, аудита и удаления локальной карточки при любой ошибке транзакции.
4. Идемпотентность scheduler и повторно доставленных заданий BullMQ.
5. Корректность PostgreSQL-расширений, индексов, OpenAPI-генерации и отсутствие ручной правки generated-кода.

## Доработки после независимого ревью

- Уточнена проверка совместимости характеристик: каждое заданное у локального ингредиента значение должно быть явно задано и совпадать у глобального кандидата.
- В отдельной миграции `20261012130000_product_search_workspace_fields` добавлены нормализованные поля и индексы для атрибутов ингредиентов и технологии составной продукции, а также индекс для поиска совпавших компонентов.
- Поиск рабочего пространства расширен на атрибуты ингредиентов, технологию и состав; поиск компонентных совпадений ограничен глобальными продуктами либо продуктами текущего заведения.
