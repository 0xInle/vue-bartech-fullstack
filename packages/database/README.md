# Пакет базы данных

Пакет `@bartech/database` хранит Prisma-схему и миграции IndieBar, сгенерированный клиент и
контролируемые сценарии начального наполнения системных данных. Бизнес-правила остаются в
предметных backend-пакетах; frontend не обращается к Prisma.

## Глобальный каталог ингредиентов

Исходный файл каталога находится в `packages/database/scripts/data/global-ingredients.json`.
Владелец продукта редактирует этот файл вручную, затем после применения миграций запускает
`pnpm catalog:seed`. Команда не входит в `postinstall`, миграции или обычный `pnpm run dev`.

Каждая запись должна содержать только обязательные поля:

```json
{
  "name": "Апельсиновый сок",
  "category": "juice"
}
```

Допустимые поля записи:

- `id` — необязательный стабильный UUID карточки;
- `name` — официальное название, обязательная строка до 160 символов;
- `category` — обязательный системный код категории;
- `brand`, `strength`, `country`, `externalIdentifier` — необязательные сведения;
- `aliases` — необязательный список подтверждённых поисковых названий.

После создания карточки сохраняйте её `id` неизменным. Идентификатор связывает запись каталога с
той же карточкой базы даже при изменении названия или атрибутов; не удаляйте его и не выдавайте
другой позиции. Первоначально файл может содержать записи без `id`: перед первой регулярной
поддержкой заполните их ID по уже загруженной локальной базе командой `pnpm catalog:backfill-ids`.
Команда сначала выполняет сухую проверку и по умолчанию не меняет файл. Для записи используйте
`pnpm catalog:backfill-ids -- --apply`. Операция разрешена только для базы `indiebar` на localhost,
требует точного взаимно-однозначного совпадения каталога и управляемых сидом глобальных карточек и
отказывается писать при любом расхождении. Запускайте её один раз на локальной базе, где уже
выполнен `pnpm catalog:seed`; в production она заблокирована.

Базовые ингредиенты без бренда допустимы: например, «Ром белый» или «Сироп маракуйя» описывают
тип продукта, а не конкретную марку. Кордиалы относятся к локальным заготовкам заведения и не
включаются в глобальный каталог.

Seed сначала идемпотентно подготавливает системные категории, категории заготовок и единицы.
Глобальные карточки, созданные seed, помечаются отдельно: повторный запуск обновляет только явно
управляемые поля этих карточек и добавляет отсутствующие алиасы. Существующие карточки, которыми
seed не владеет, пропускаются. Локальные карточки не выбираются и не изменяются.

Если у записи каталога указан стабильный `id`, seed ищет карточку только по нему. Ключ идентичности
используется как запасной способ поиска только для записей без `id`. Если `id` и ключ идентичности
указывают на разные карточки либо новый ключ уже занят другой карточкой, импорт прекращается с
понятной ошибкой до обновления этой записи.

Не запускайте команду, пока в исходном файле есть незавершённый JSON. При ошибке валидатор
указывает номер записи и проблемное поле. Сам файл не изменяется seed-командой.

## Миграции и Prisma

Схема разделена по предметным файлам в `prisma/`. Изменения схемы сопровождаются версионируемой
миграцией. Для проверки схемы используется `pnpm --filter @bartech/database prisma:validate`, для
генерации клиента — `pnpm prisma:generate`.

Команда `pnpm --filter @bartech/database internal-user -- create <email> [permissions]` создаёт
внутренний аккаунт `PENDING_ENROLLMENT`, пишет событие аудита и выводит одноразовый setup-token.
`pnpm --filter @bartech/database internal-user -- reset <email>` отзывает сессии, очищает MFA,
фиксирует операторский сброс и выдаёт новый токен. Доступные разрешения перечислены в
`DATA_MODEL.md`; токен передаётся сотруднику вне приложения.
Сброс отклоняется для отключённого (`DISABLED`) аккаунта и не включает его.
Для разрешённого MFA-сброса счётчик ошибок TOTP и отметка отключённого фактора очищаются.
Команда `pnpm --filter @bartech/database internal-user -- disable <email>` отключает аккаунт,
отзывает сессии и challenge и записывает событие аудита.
