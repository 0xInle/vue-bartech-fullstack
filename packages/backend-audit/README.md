# Журнал действий backend

Пакет `@bartech/backend-audit` отвечает за авторизованное чтение неизменяемых событий `AuditEvent`.
Создание записей остаётся в пакетах владельцев предметных операций: продуктовые события записываются
в транзакциях `backend-products`, события команды — в `backend-organizations`.

`AuditReadService.list` заново получает рабочее пространство через публичный API
`OrganizationsService`. Заведение определяется актуальным членством; `view_history` разрешает
полную историю подтверждённой области. Без этого права сервис возвращает только собственные
продуктовые действия и адресованные пользователю изменения роли/прав/временной ответственности.
Идентификаторы scope в query не принимаются.

Фильтры даты, типа события, автора и сущности сужают серверную выборку. Endpoint
`GET .../history/authors` строит варианты фильтра только по авторам событий, уже доступных
пользователю в этом scope и с теми же фильтрами даты, типа и сущности. Он возвращает только ID и
имя профиля; не перечисляет команду, не раскрывает авторов закрытых событий и пропускает удалённые
или обезличенные профили. Порядок стабилен
(`createdAt DESC, id DESC`), страница по умолчанию содержит 30, максимум 50 записей. Курсор
кодирует пару времени и ID. Ответ содержит только отображаемые сведения; метаданные очищаются по
списку безопасных полей, адрес электронной почты и содержимое карточек не читаются.

HTTP-адаптер расположен в `apps/backend/src/audit`; OpenAPI и клиент обновляются командой
`pnpm api:generate`. Продуктовые правила и перечень событий описаны в
[`docs/specs/2026-10-15-stage-8-audit-history.md`](../../../docs/specs/2026-10-15-stage-8-audit-history.md).

## Покрытие и ограничения

- Источники событий: создание/изменение/архивирование/восстановление продукции, сопоставление
  локального ингредиента с каталогом, создание/отзыв/истечение/принятие приглашения, создание
  заведения, смена роли, делегирование
  прав и завершение временной ответственности.
- Безвозвратное удаление продукции, закрытие компании/заведения и служебный доступ ещё не имеют
  реализованных producer-сценариев в текущем backoffice; фиктивные события для них не создаются.
- Начало временной ответственности пока не создаётся: в текущем срезе нет соответствующего
  пользовательского бизнес-сценария.
- Старые события смены роли/прав без `subjectUserId` не связываются с адресатом задним числом и
  потому недоступны в персональной истории сотрудника. Они остаются в полной истории уполномоченных.
- Неизвестный/удалённый автор показывается как «Аккаунт недоступен»; неизвестная сущность остаётся
  без названия. Чтение истории карточек не восстанавливает старое содержимое.
