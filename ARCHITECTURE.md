# Архитектура MVP BarTech

## Назначение документа

Документ определяет техническую архитектуру MVP BarTech: состав приложений и инфраструктуры, границы модулей, направление зависимостей, способы хранения и передачи данных, требования безопасности и правила разработки.

Документ не меняет бизнес-логику. Источниками продуктовых правил являются:

- `REGISTRATION_FLOW.md`;
- `AUTHENTICATION_FLOW.md`;
- `ROLES_AND_PERMISSIONS.md`;
- `PRODUCT_MODEL.md`;
- `COMPANY_AND_VENUE_LIFECYCLE.md`;
- `MVP_SCOPE.md`.

Концептуальные сущности определены в `DATA_MODEL.md`, а пользовательское представление — в `UI_AND_NAVIGATION.md`. Если техническое решение расходится с этими документами, реализация не выбирает новое поведение самостоятельно: сначала уточняется документация нужного уровня.

## Архитектурные цели

- Быстро выпустить MVP без преждевременного перехода к микросервисам.
- Сохранить понятные границы предметных областей и возможность независимо развивать их.
- Не смешивать данные компаний и заведений.
- Использовать распространённые подходы, знакомые разработчикам Nuxt, NestJS и PostgreSQL.
- Позволить масштабировать отдельные процессы без переписывания бизнес-модели.
- Минимизировать скрытую автоматизацию и не добавлять инфраструктуру без текущей задачи.
- Считать backend единственным доверенным источником бизнес-правил и разрешений.

Перед началом реализации выбираются актуальные стабильные версии технологий по их официальной документации. Предварительные, экспериментальные версии и кандидаты на выпуск (`RC`) без отдельного решения не используются. Точные версии фиксируются в `pnpm-lock.yaml` и Docker-образах.

## Общая схема

```text
Пользователь
    │
    ▼
Nuxt 4 PWA
PrimeVue + Tailwind CSS
Nuxt Layers
TanStack Query
VeeValidate + Zod
    │
    │ REST /api/v1
    ▼
NestJS + Express
модульный монолит
    │
    ├── PostgreSQL + Prisma
    ├── Redis + BullMQ
    ├── S3-совместимое хранилище
    ├── почтовый провайдер
    └── антивирусная проверка файлов
```

Публичный лендинг, клиентское рабочее пространство и внутренний backoffice входят в одно Nuxt-приложение, но имеют разные маршруты, макеты и правила доступа. Backend является отдельным приложением. Фоновые обработчики запускаются отдельным процессом из того же backend-кода.

## Репозиторий

Используется monorepo на `pnpm workspaces`.

```text
apps/
├── web/                         # Nuxt: лендинг, PWA, CRM и backoffice
└── backend/                     # NestJS: HTTP API и точка сборки worker

packages/
├── backend-identity/            # аккаунты, сессии и восстановление доступа
├── backend-organizations/       # компании, заведения и приглашения
├── backend-access/              # роли, разрешения и передача управления
├── backend-products/            # коктейли, заготовки, гарниры и архив
├── backend-catalog/             # глобальные и локальные ингредиенты
├── backend-support/             # обращения и служебный доступ
├── backend-audit/               # журнал значимых действий
├── backend-analytics/           # продуктовые события MVP
├── database/                    # Prisma schema, миграции и доступ к БД
└── api-client/                  # код, сгенерированный из OpenAPI

tooling/                         # общие настройки TypeScript, ESLint и Prettier
infrastructure/                  # Docker и конфигурация развёртывания
```

Названия пакетов могут уточняться при составлении плана, но границы предметных областей сохраняются. Пакет не создаётся для каждой таблицы или сущности.

`apps/backend` является точкой композиции: запускает NestJS, конфигурацию, HTTP, проверки состояния и worker. Предметная логика находится в `packages/backend-*`. Пакеты не импортируют приложения.

Nx и Turborepo в MVP не используются. При заметном росте времени сборки можно добавить Turborepo, не меняя структуру workspace.

## Frontend

### Основные технологии

- Nuxt 4 и Vue 3;
- TypeScript в строгом режиме;
- PrimeVue 4 в `styled mode`;
- тема Aura как исходная основа и собственные токены дизайна BarTech;
- Tailwind CSS для компоновки, адаптивности и локальных стилей;
- TanStack Query for Vue для серверных данных;
- VeeValidate и Zod для форм;
- Orval-клиент, сгенерированный из OpenAPI;
- PWA без офлайн-работы с бизнес-данными.

Pinia в MVP не используется. Данные backend принадлежат TanStack Query, локальное состояние компонента — стандартной реактивности Vue, небольшое общее состояние Nuxt — `useState`. Если позднее появится сложное клиентское состояние, хранилище добавляется под конкретную задачу.

### Рендеринг

Публичный лендинг использует SSR или предварительную генерацию для скорости, SEO и корректной индексации. Авторизованная CRM после входа работает преимущественно как клиентское приложение. Конкретные `routeRules` определяются при реализации маршрутов.

### Nuxt Layers

Крупные пользовательские разделы организуются как локальные Nuxt Layers:

```text
apps/web/
├── app/                         # ядро приложения и общая оболочка
│   ├── components/ui/           # обёртки над PrimeVue
│   ├── layouts/                 # публичный, CRM и internal макеты
│   ├── middleware/              # аутентификация и доступ
│   └── plugins/                 # PrimeVue, TanStack Query и инфраструктура
│
├── layers/
│   ├── cocktails/
│   ├── preparations/
│   ├── garnishes/
│   ├── ingredients/
│   ├── search/
│   ├── archive/
│   ├── team/
│   └── support/
│
└── shared/
    └── product-core/            # общий редактор состава и связанные примитивы
```

Каждый слой содержит относящиеся к нему страницы, компоненты, composables, запросы и схемы форм. Точный набор слоёв уточняется по плану MVP: мелкая возможность не обязана становиться отдельным Layer.

Правила зависимостей:

- слой владеет своей логикой и маршрутами;
- общая логика выносится только после появления реального повторного использования;
- внутренние файлы слоя не являются публичным API для других слоёв;
- необходимая связь проходит через публичный вход слоя или общую основу;
- циклические зависимости запрещены;
- предметные слои не содержат авторизацию, HTTP-клиент или общую тему приложения;
- удаление слоя может потребовать удаления его явной регистрации или связанного пункта навигации, но не должно вызывать каскадную переработку других разделов.

Layers являются частями одного Nuxt-приложения, а не микрофронтендами и не развёртываются независимо.

### Маршруты и рабочий контекст

Текущие компания и заведение находятся в URL:

```text
/app/companies/{companyId}/venues/{venueId}/cocktails
```

Идентификаторы контекста входят в ключи TanStack Query. Backend заново проверяет доступ при каждом запросе; наличие идентификатора в URL не предоставляет разрешение.

Поиск, фильтры, сортировка и вкладки, которые должны переживать обновление страницы, также отражаются в URL. Токены авторизации не хранятся в `localStorage`.

### UI-компоненты

PrimeVue предоставляет поведение базовых компонентов. Общий внешний вид и соглашения BarTech оформляются обёртками вроде `AppButton`, `AppDrawer` и `AppFormField`. Предметные компоненты, например `GarnishForm`, остаются внутри своего слоя.

Кастомизация PrimeVue выполняется через theme tokens и Pass Through API. Изменение внутренних классов библиотеки хрупкими глобальными селекторами запрещено.

### Формы

VeeValidate управляет состоянием, динамическими массивами, ошибками и отправкой формы. Zod описывает клиентскую схему. PrimeVue отвечает только за визуальные поля.

Frontend-проверка улучшает пользовательский опыт, но не является защитой. Backend независимо проверяет все данные. Серверные ошибки полей преобразуются в ошибки VeeValidate.

### PWA

PWA устанавливается на телефон и компьютер. Service Worker кеширует оболочку и статические ресурсы, но не предоставляет надёжное офлайн-хранилище бизнес-данных.

Просмотр, создание и редактирование продукции требуют сети. При потере соединения приложение показывает постоянное сообщение и блокирует изменяющие действия. Офлайн-очередь, локальная база и разрешение конфликтов не входят в MVP.

## Backend

### Основные технологии

- актуальная стабильная Node.js LTS;
- NestJS 11;
- стандартный Express adapter;
- TypeScript в строгом режиме;
- PostgreSQL;
- Prisma ORM стабильной версии;
- Redis и BullMQ;
- Pino для структурированных логов.

Backend является модульным монолитом. Микросервисы, CQRS для всех операций и отдельная шина событий в MVP не используются.

### Внутренняя структура предметного пакета

```text
HTTP controller
    ▼
прикладной сервис / сценарий
    ▼
domain rules
    ▼
repository interface
    ▼
Prisma repository
```

- Контроллер принимает HTTP-запрос, запускает проверку DTO и вызывает один прикладной сценарий.
- Прикладной сервис задаёт транзакционную границу и координирует предметные операции.
- Доменные правила не зависят от HTTP, Vue, Prisma и BullMQ.
- Репозиторий скрывает способ хранения данных.
- Контроллер не обращается к Prisma напрямую.
- Универсальный `BaseRepository` не создаётся: репозитории отражают реальные операции предметной области.
- Транзакционный контекст передаётся явно между участвующими репозиториями.

### Проверка данных

Backend использует DTO-классы, `class-validator`, `class-transformer` и глобальный `ValidationPipe`.

Запрос с неизвестными полями отклоняется. Попытка передать защищённое поле, например роль или `companyId`, через DTO редактирования не должна менять его значение. После проверки формы данных прикладной сервис выполняет предметные проверки, включая уникальность, состояние сущности, зависимости и полномочия.

## REST API и контракт

Публичный контракт backend — версионированный REST API с префиксом `/api/v1`.

NestJS формирует OpenAPI-схему через `@nestjs/swagger`. Orval создаёт в `packages/api-client`:

- TypeScript-типы запросов и ответов;
- функции HTTP-запросов;
- TanStack Query composables и query keys.

Сгенерированный код не редактируется вручную. Изменение DTO или endpoint сопровождается повторной генерацией клиента. CI проверяет, что сгенерированный результат соответствует OpenAPI-контракту.

GraphQL в MVP не используется. Правила пагинации, сортировки и фильтров определяются в спецификации соответствующего модуля.

### Формат ошибок

API возвращает единый формат Problem Details с расширениями BarTech:

```json
{
  "type": "https://bartech.ru/problems/duplicate-name",
  "title": "Название уже используется",
  "status": 409,
  "code": "PRODUCT_NAME_CONFLICT",
  "detail": "В заведении уже есть активный гарнир с таким названием",
  "fieldErrors": {
    "name": ["Введите другое название"]
  },
  "requestId": "req_..."
}
```

`code` является стабильным машинным идентификатором. Пользовательские сообщения написаны на русском. Stack trace, SQL и внутренние сведения клиенту не возвращаются. Глобальный exception filter приводит все ошибки к этому контракту.

## Аутентификация и сессии

Используются серверные сессии, а не JWT в браузере.

- Браузер получает случайный непрозрачный токен в cookie с `HttpOnly`, `Secure`, `SameSite=Lax` и префиксом `__Host-`.
- В PostgreSQL хранится только хеш токена.
- Для каждого браузера и устройства создаётся отдельная сессия.
- Сессия действует 30 дней с последней активности и не более 90 дней с момента создания.
- Можно завершить текущую или все сессии.
- Пароли хешируются Argon2id.
- Одноразовые ссылки и коды также хранятся только в виде хеша.
- Авторизационные токены не доступны JavaScript и не сохраняются в `localStorage`.

Nuxt и API публикуются на одном origin: `/` обслуживает Nuxt, `/api` — NestJS через reverse proxy.

## Изоляция компаний и заведений

Все клиенты используют общую PostgreSQL-базу с логической tenant-изоляцией.

Каждая клиентская запись имеет явную принадлежность компании или заведению. В запросе формируется проверенный контекст:

```ts
{
  userId,
  companyId,
  venueId,
  role,
  permissions
}
```

Правила:

- репозиторий не получает один только идентификатор клиентской сущности, если для проверки необходимы `companyId` или `venueId`;
- внешние идентификаторы не считаются доказательством доступа;
- внешние ключи и составные ограничения не позволяют связать сущности разных компаний или заведений;
- глобальный каталог отделён от клиентских данных;
- служебный доступ проверяется отдельным контекстом;
- отсутствие tenant-контекста означает запрет, а не неограниченный запрос.

PostgreSQL Row-Level Security в MVP не включается, чтобы не усложнять Prisma, пул соединений, транзакции, доступ шеф-барменов и backoffice. Границы репозиториев сохраняют возможность добавить RLS позднее.

## Роли и разрешения

Авторизация реализуется собственным типизированным `PermissionService`, а не универсальным policy-фреймворком.

`PermissionService` рассчитывает итоговые разрешения из:

- должности;
- области компании или заведения;
- делегированных разрешений;
- временной ответственности;
- состояния аккаунта, компании и заведения.

Контроллер объявляет необходимое разрешение через декоратор, Guard выполняет первичную проверку, а прикладной сервис повторно проверяет область и состояние конкретных сущностей.

Frontend получает доступные действия, чтобы не показывать недоступные элементы, но это не заменяет серверную проверку. Изменения ролей, разрешений и временной ответственности выполняются транзакционно и записываются в аудит.

В MVP разрешения не кешируются на backend: отозванный доступ должен прекращаться без периода устаревшего кеша.

## PostgreSQL и Prisma

PostgreSQL является единственным источником актуальных бизнес-данных.

- Prisma используется для типизированных обычных запросов и миграций.
- Prisma schema разбивается на несколько файлов по предметным областям.
- Для возможностей PostgreSQL, которые неудобно выразить Prisma, разрешён параметризованный SQL.
- Миграции создаются, проверяются и сохраняются в Git.
- Изменение production-схемы вручную запрещено.
- Миграции по возможности обратно совместимы с предыдущей версией приложения.

Универсальный `deletedAt` не добавляется ко всем таблицам. Архив, ожидание удаления, закрытие и отзыв доступа представлены предметными состояниями. После согласованного срока данные физически удаляет фоновая задача.

Моменты времени хранятся в UTC через `timestamptz`. Сроки рассчитывает backend. Frontend отображает время в часовом поясе устройства и не определяет истечение доступа по локальным часам.

## Поиск

Поисковым движком MVP является PostgreSQL.

Используются:

- полнотекстовый поиск с индексами GIN;
- расширение `pg_trgm` для опечаток и похожих написаний;
- нормализация регистра, пробелов, символов и `е/ё`;
- русские и английские псевдонимы;
- подготовленные варианты транслитерации там, где они нужны каталогу;
- ранжирование: точное название, начало названия, псевдоним, похожее написание;
- обязательная фильтрация по области доступа до выдачи результата.

Целевое время ответа поискового API при обычной нагрузке — до 200–300 мс. Медленные запросы фиксируются для последующей оптимизации. Elasticsearch и OpenSearch в MVP не используются. При росте объёма поисковый контракт позволит вынести индекс в отдельный сервис.

## Одновременные изменения и аудит

Для обычного редактирования продукции действует правило: последнее успешно сохранённое изменение становится актуальным. Оптимистическая блокировка и хранение предыдущих редакций не входят в MVP.

Транзакционно значимые операции, связанные с ролями, приглашениями, удалением, закрытием и передачей управления, повторно проверяют актуальное состояние перед записью и выполняются целиком либо не выполняются.

Журнал MVP фиксирует автора, время, действие и объект, но не хранит полное содержимое карточки до и после изменения. Он не является историей версий.

## Фоновые задачи

BullMQ и Redis используются для:

- отправки писем;
- подготовки выгрузок;
- обработки кандидатов в глобальный каталог;
- антивирусной проверки;
- продуктовой аналитики;
- повторения временно неудачных операций;
- задач физического удаления после окончания срока ожидания.

Worker запускается отдельным процессом, но использует те же предметные пакеты. При росте нагрузки worker масштабируется независимо от HTTP-процесса.

Все обработчики проектируются идемпотентными. Повторная доставка задачи не должна создавать повторное приглашение, повторно менять роль или производить другое необратимое действие.

### Transactional Outbox

Если успешная транзакция PostgreSQL должна гарантированно привести к фоновой операции, в той же транзакции создаётся запись Outbox. Отдельный обработчик публикует её в BullMQ и отмечает обработанной.

Outbox используется только для критичных связей между бизнес-записью и фоновым действием: приглашения, письма безопасности, выгрузки, глобальный каталог и будущие интеграции. Обычное редактирование карточки Outbox не создаёт.

## Электронная почта

Предметные пакеты используют интерфейс `EmailService`, не зависящий от провайдера.

- Письма отправляются через BullMQ.
- Временные ошибки повторяются с ограниченным увеличением задержки между попытками.
- Шаблоны хранятся в репозитории и написаны на русском.
- В production подключается транзакционный сервис, доступный в российской инфраструктуре.
- Локально используется Mailpit.
- Секретная ссылка содержит случайный токен, в базе хранится только его хеш.

## Файлы и объектное хранилище

PostgreSQL хранит метаданные файлов и ключ объекта, а содержимое находится в S3-совместимом хранилище. Предметный код использует интерфейс `FileStorage`.

- Локальная разработка использует MinIO.
- Production-провайдер выбирается в российской инфраструктуре.
- Выгрузки имеют ограниченный срок хранения и очищаются фоновой задачей.
- Ссылки на скачивание краткоживущие и требуют действующего доступа.
- Будущие изображения продукции используют тот же интерфейс, но не входят в MVP.

### Вложения поддержки

Разрешаются только утверждённые форматы, первоначально `xlsx`, `xls`, `csv`, `pdf`, `png` и `jpg`, с ограничением размера до 20 МБ на файл. Перед реализацией список и лимит сверяются со спецификацией поддержки.

Проверяется расширение и фактический тип содержимого. Файл сначала попадает в закрытый карантин, затем отдельный worker проверяет его через ClamAV. Скачать вложение можно только после успешной проверки. Сервер не исполняет содержимое файла как код.

## Backoffice BarTech

Внутренние сотрудники используют отдельный тип аккаунта и отдельный контур авторизации.

- Вход находится в закрытом разделе `/internal`.
- Для внутренних аккаунтов обязательна двухфакторная защита.
- `InternalUser` не может получить клиентскую роль или принять клиентское приглашение.
- Доступ запрещён по умолчанию.
- Обращение пользователя само по себе не открывает данные компании.
- Для работы с продукцией требуется действующий `SupportAccessGrant`.
- Конкретная работа выполняется в ограниченной `ServiceSession`.
- Сотрудник поддержки не входит от имени клиента и не получает его сессию.
- Управление компаниями, заведениями, сотрудниками, ролями и безопасностью технически запрещено.
- Отзыв разрешения или окончание семи дней немедленно прекращает доступ.
- Служебные действия журналируются отдельно.

## Продуктовая аналитика

В MVP используется собственный минимальный сбор событий через интерфейс `ProductAnalytics`.

События передаются на backend, обрабатываются через BullMQ и сохраняются отдельно от аудита и технических логов. Допускаются только заранее определённые события и свойства. Не собираются:

- email и ФИО;
- содержимое техкарт;
- названия пользовательской продукции;
- введённые поисковые строки;
- пароли, токены и cookie.

Аналитика оценивает активацию, использование поиска, создание первой продукции, приглашение команды, возврат пользователей и использование выгрузки. Интерфейс позволяет позднее перенести поток в специализированное хранилище без изменения экранов приложения.

PostHog и отдельный ClickHouse в MVP не разворачиваются.

## Кеширование и обновления в реальном времени

В MVP нет серверного кеша продукции, поиска, ролей и разрешений. PostgreSQL остаётся единственным актуальным источником, а TanStack Query уменьшает повторные запросы в браузере.

Redis используется для BullMQ, ограничения частоты запросов и технической координации. Бизнес-кеш добавляется только после измерения реальной нагрузки.

WebSocket и серверные обновления в реальном времени отсутствуют. TanStack Query обновляет данные после изменений, переходов, возвращения во вкладку или явного обновления.

## Безопасность

- Применяется принцип запрета по умолчанию и минимальных привилегий.
- Авторизация проверяется на каждом защищённом запросе.
- Reverse proxy ограничивает аномальную частоту запросов с IP.
- NestJS отдельно ограничивает вход, восстановление пароля, письма, приглашения и поиск.
- Счётчики распределённого ограничения частоты запросов хранятся в Redis.
- CAPTCHA в MVP отсутствует.
- Helmet задаёт безопасные HTTP-заголовки и Content Security Policy.
- Production API не открывает CORS для сторонних origin.
- Изменяющие запросы защищаются CSRF-токеном и проверкой `Origin`.
- Ограничиваются размеры JSON, форм и файлов.
- Prisma или параметризованный SQL защищают запросы к базе.
- Секреты не находятся в Git, frontend, логах и Docker-образах.
- OpenAPI UI не публикуется открыто в production.
- Соединения, резервные копии и объектное хранилище используют доступное шифрование инфраструктуры.
- Критические уязвимости production-зависимостей проверяются в CI.

Отдельная документация безопасности позднее уточнит обработку персональных данных, политику секретов, процедуры инцидентов и восстановление внутренних аккаунтов.

## Наблюдаемость

Технические логи пишутся через Pino в структурированном JSON.

- Каждый HTTP-запрос, фоновая задача и связанная ошибка получают `requestId` или корреляционный идентификатор.
- Пароли, токены, cookie, персональные данные и содержимое техкарт маскируются или не журналируются.
- Необработанные ошибки поступают в централизованный сборщик.
- `/health/live` проверяет, что процесс работает.
- `/health/ready` проверяет готовность принимать трафик и критические зависимости.
- Доступность PostgreSQL, Redis и объектного хранилища контролируется отдельно.
- Бизнес-аудит, продуктовая аналитика и технические логи не смешиваются.

Полноценная распределённая трассировка и расширенные метрики не входят в MVP. Архитектура сохраняет возможность подключить OpenTelemetry после появления реальной нагрузки.

## Развёртывание

Компоненты упаковываются в Docker.

```text
reverse proxy
├── /      → web
└── /api   → backend

backend infrastructure
├── PostgreSQL
├── Redis
├── S3-compatible storage
├── worker
└── ClamAV
```

Используются три среды: локальная, тестовая и production. Конфигурация передаётся через переменные окружения и секреты deployment.

Для MVP допустим один сервер приложений с отдельными контейнерами. PostgreSQL, Redis и объектное хранилище могут быть управляемыми сервисами или отдельными защищёнными компонентами. Kubernetes не используется.

Основная база, персональные данные, объектное хранилище, резервные копии, продуктовая аналитика и связанные production-сервисы размещаются в российской инфраструктуре.

## CI/CD

GitHub Actions выполняет:

```text
Pull request
└── pnpm install --frozen-lockfile
    ├── lint
    ├── typecheck
    ├── проверка Prisma schema и миграций
    ├── генерация OpenAPI-клиента
    ├── проверка актуальности сгенерированного кода
    └── build web + backend + worker

merge в основную ветку
└── Docker build
    └── развёртывание тестовой среды

production
└── ручное подтверждение
    ├── проверка резервной копии
    ├── применение миграций
    ├── развёртывание контейнеров
    └── проверка готовности
```

Production не обновляется автоматически после каждого слияния. При неуспешной проверке готовности новая версия не принимает трафик. Предыдущий образ сохраняется для отката приложения.

## Резервное копирование

PostgreSQL резервируется не реже одного раза в сутки. Копии шифруются, хранятся отдельно от основного сервера и сохраняются ориентировочно 30 дней согласно `MVP_SCOPE.md`.

Восстановление периодически проверяется на практике. Должна существовать техническая возможность восстановить систему и, при необходимости, данные отдельной компании. Пользовательская выгрузка не заменяет инфраструктурную резервную копию.

## Правила качества кода

- TypeScript работает в строгом режиме.
- Используются общий ESLint flat config, Prettier и EditorConfig.
- `any` запрещён по умолчанию и допускается только как явно объяснённое исключение.
- ESLint проверяет границы frontend Layers и backend-пакетов.
- Циклические импорты запрещены.
- Из корня доступны единые команды `lint`, `typecheck`, `format` и `build`.
- Husky и обязательные pre-commit hooks в MVP не используются.
- Человекочитаемая документация и пользовательские сообщения написаны на русском; код, имена файлов, API, таблиц и машинные идентификаторы — на английском.
- Реализация сверяется с официальной документацией фактически установленных версий библиотек.

## Политика тестов

До завершения реализации MVP:

- тестовые библиотеки и тестовые файлы не добавляются без отдельного согласования;
- unit, integration и e2e-тесты не пишутся и не запускаются без прямой команды владельца продукта;
- форматирование, lint, typecheck и build не считаются тестами и используются при разработке;
- код сохраняет тестопригодные границы: внедрение зависимостей, прикладные сервисы, доменные функции и интерфейсы репозиториев.

После реализации MVP тесты добавляются точечно по риску. Первый приоритет:

- расчёт разрешений;
- делегирование и отзыв прав;
- временная ответственность и передача управления;
- несовместимые роли;
- tenant-изоляция;
- приглашения и транзакционные операции;
- запрет оставить действующее заведение без управления.

Простой frontend не покрывается unit-тестами без конкретной ценности. Небольшой набор e2e-сценариев рассматривается отдельно после стабилизации MVP.

## Что осознанно отсутствует в MVP

- микросервисы;
- Kubernetes;
- GraphQL;
- PostgreSQL RLS;
- Elasticsearch или OpenSearch;
- server-side кеш бизнес-данных;
- WebSocket и обновления в реальном времени;
- работа прежде всего без сети (`offline-first`) и синхронизация локальных изменений;
- хранение и сравнение редакций продуктовых карточек;
- универсальный soft delete;
- сложная система продуктовой аналитики;
- полная OpenTelemetry-трассировка;
- автоматические тесты без отдельного согласования.
